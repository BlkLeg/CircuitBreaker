## What to be careful about, in order of how much it will cost you

1. **Six clusters carry one adversarial review, not two.** `snapshot`, `auditchain`,
   `oauth`, `websockets`, `ssrf` and `listener` were remediated, but their second
   reviewers were killed by a session limit before they ran. Everything else in wave 3 was
   reviewed, remediated, and re-reviewed. If you are looking for what is most likely to be
   wrong, look there first — the Wave 3 table in the report marks them.

2. **A green suite is not evidence here.** The first adversarial round over fifteen
   clusters produced **7 blockers, 17 majors and 24 tests proven vacuous**, against code
   whose tests were all passing. Among them: a fix that broke TLS for every webhook behind
   an egress proxy, a fix that turned a data-shape bug into an INSERT failure on any TXT
   record carrying a NUL, and a migration that aborted on exactly the rows it existed to
   repair. If you fan out again, budget for the review, not just the fix.

3. **Do not trust a status row you did not verify against the tree.** During this pass two
   rows in the report claimed a fix that was not there. R12 is the instructive one: the
   regression was fixed in `telemetry_ingest_worker` and left live in a byte-identical copy
   in `workers/discovery.py`, and the report said it was closed. A reviewer caught both the
   code and the row. The two workers now share one implementation
   (`workers/stream_limits.py`) because two copies of it was the actual defect.

4. **Ruff resolves differently under `tests/` than under `apps/backend/`.** The backend has
   `select = ["E", "F", "I", "UP", "ASYNC"]` and `line-length = 100` in its own
   `pyproject.toml`; the repo root has no `pyproject.toml` at all, so anything under the
   root `tests/` directory resolves to ruff's ambient config instead. Running a bare
   `ruff check --fix` / `ruff format` over `tests/` will reflow pre-existing code to 88
   columns and apply rules this project never selected. Lint backend files **from
   `apps/backend/`**; for root `tests/` files, match the file you are editing and compare
   against a HEAD baseline before believing you introduced something.

5. **`.pre-commit-config.yaml` declares gitleaks, ruff, ruff-format and `mypy --strict`,
   but no hook is installed in `.git/hooks/`.** Nothing runs it on commit. Check by hand.

6. **Disjoint file ownership is the only thing that makes a fan-out safe.** Every agent in
   this pass was given an explicit, non-overlapping file list. The two places work leaked
   were both scoping mistakes in the *assignment*, not collisions: B28's cluster owned
   `auth_service.py` while the unrecorded token was minted one layer up in `api/auth.py`,
   and R12's owner did not own the second copy in `workers/discovery.py`.

## How to verify

Both of these must be green, and the backend one must be run **without** narrowing:

```
.venv/bin/pytest tests -q                                  # repo root, ~7s, 326 passed
cd apps/backend && CB_ALLOW_DEGRADED_DEPENDENCIES=true CB_ALLOW_DIRECT_EGRESS=true \
  PYTHONPATH=src ../../.venv/bin/pytest tests -q -p no:randomly
```

The backend suite spins up its own Postgres testcontainer per session, so parallel runs are
isolated — that is what made the fan-out safe.

Its `addopts` carries `-x`, so a green tail is never proof the whole suite ran; check the
count. That used to be worse: `test_full_endpoint_inventory_matches_runtime_routes` failed
with a bare `assert 6 == 4` on any checkout without a built `apps/frontend/dist`, and being
the fiftieth test to run it hid the entire suite behind one cryptic failure. That is fixed
(B51), but the `-x` habit of checking the count is still the right one.

## Things that are done — do not redo them

* **The Alembic revision.** Head is `0104_bugbounty_20260826`, chaining from `7d2e4a81c6f3`.
  It carries B14's `app_settings.audit_chain_checkpoint_hash`, B13's composite index on
  `listener_events`, and B34's data repair. It was verified against a real PostgreSQL 16
  through upgrade → downgrade → re-upgrade across the whole 115-revision chain, with
  fixtures for all four shapes of `properties_json`. One trap is recorded in the revision
  itself: `properties_json::text` renders an escape **doubled**, so a repair that strips
  only the single-backslash form silently skips every row it exists to fix.
* **Backend tests build schema from `models.Base.metadata.create_all`, not Alembic.** A
  missing revision is therefore invisible to the suite and shows up only as a broken
  upgrade. The composite index is declared in `models.py` as well as in the revision for
  exactly this reason; keep them together.
* **The `listener_events` retention purge is wired** into `main.py` at 03:30, clear of the
  scan-result (03:00), audit-log (03:15) and probe-run (03:20) purges — they take an
  advisory lock keyed on job id, so overlapping ones merely queue.
* **`VERSION` is `0.4.0`** and `package.json` / `apps/frontend/package.json` move with it
  (GOV-09, `tests/build/test_version_parity.py`).
* **`CB_DATA_DIR` is redirected to a per-run temp dir in `apps/backend/tests/conftest.py`.**
  This was B37, and it was not merely tree residue: with the variable unset,
  `vault_service` fell back to `cwd/data`, generated a real Fernet key into
  `apps/backend/data/.env` — gitignored, so invisible in `git status` — and a later run
  loaded that stale key instead of generating a fresh one. Leave the redirect in place.
