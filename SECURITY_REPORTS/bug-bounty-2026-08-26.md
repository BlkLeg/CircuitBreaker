**35 confirmed defects against `1.0.0-rc.4`, plus 15 more found while fixing them.**

Of the original 35: six were fixed and committed on 2026-08-26; sixteen more carry a fix
in the **uncommitted working tree**; thirteen remain. See
[Remediation in progress](#remediation-in-progress--started-2026-08-26-tree-at-2d6368ac)
for exactly which, what is still running, and the thirteen regressions the remediation

Unlike every other document indexed in [`README.md`](./README.md), this one describes
the tree as it stands now rather than as it stood in March or June. Treat the open
findings as live.

## Provenance, and what "confirmed" means here

The findings were produced on 2026-08-26 by a multi-agent hunt over `dev` at `f483bcb3`.
Each finding was generated by one agent and then put to independent adversarial
verifiers whose instructions were to *refute* it; only findings that survived are
recorded. The `reasoning` field of every entry in
[`bug-bounty-2026-08-26-findings.json`](./bug-bounty-2026-08-26-findings.json) is that
refutation attempt written out — which upstream guard was checked and why it does not
apply, what was measured, what configuration the path needs.

That is a real bar, and it is not the same as a human having reproduced each one.

**Verification status is per finding, and it is not uniform:**

- The **six fixed** findings were each re-verified by hand before being touched: the
  defect was reproduced with a test, the fix applied, and the test re-run against the
  restored defect to confirm it names the bug. Those are proven.
- The **twenty-nine open** findings carry the hunt's verification only. They have not
  been independently reproduced. One of the six turned out to overstate its own severity
  on inspection (see B04 below), so read the open ones as strong leads rather than as
  settled fact, and confirm before acting.

The fix text quoted under each open finding below is the hunt's own, reproduced verbatim
rather than paraphrased, precisely because it has not been independently checked — line
numbers and helper names in it are as of `f483bcb3` and some have since moved.

### The one correction to the source data

**B04 was reported as four *unauthenticated* write routes. That is wrong.** The
`discovery` router is mounted with `dependencies=[require_scope("read", "*")]`, so the
routes always required an authenticated principal. The actual defect is narrower and
still serious: four routes that create `Hardware` rows and rewrite topology were gated
by a *read* scope, so any viewer could call them. The fix is the same; the severity
claim in the source data is not.

This is the reason the twenty-nine open findings are labelled as leads. One in six of
the ones examined closely was wrong about its own reachability.

### Four defects found while fixing, not present in the 35

- **`POST /api/v1/auth/service-account` returned 500 to every call.** The route is
  decorated `@limiter.limit` but declared no `response: Response`, so slowapi raised
  `parameter 'response' must be an instance of starlette.responses.Response`. The whole
  service-account feature was unreachable through the API and no test called it. Fixed in
  `bac26cb8` with `tests/test_rate_limited_routes_declare_response.py`, which now checks
  all 39 rate-limited routes structurally.

- **The SEC-06 write gate accepted a read-only scope as authorization for a mutating
  route.** `_has_write_gate` treated any `require_role`/`require_scope` dependency as
  sufficient, and could not do better: both factories return an inner `_dep`, so
  `require_scope("read", "*")` and `require_scope("write", "*")` report the same qualname.
  This is why B04 was invisible to the gate built to catch exactly that class. `core.rbac`
  now tags each `_dep` with what it declares and the gate judges the declaration
  (`9e1fcd82`).

- **`create_token` mints no `jti` or `iat`.** Two service-account tokens minted in the
  same second with the same claims are byte-identical, so rotation returned the caller
  their existing secret. Service-account mints now carry a `jti` (`bac26cb8`).

- **The health entries in `endpoint_policy.json` never matched runtime.** Stacked
  `@app.head` and `@app.get` decorators register two single-method routes rather than one
  answering both, so the combined `["GET", "HEAD"]` entries matched nothing and left
  `test_runtime_routes_reconcile_with_public_endpoint_policy` red (`9e1fcd82`).

### B05 — Zip bomb in docs import: ZIP members are fully decompressed before the per-file size check

**Location:** `apps/backend/src/app/api/docs.py:95`  ·  **Severity:** HIGH  ·  **Hunt id:** `F05`

In apps/backend/src/app/api/docs.py, add two constants beside the existing ones (near line 23):

    _MAX_IMPORT_ZIP_ENTRIES = 500
    _MAX_IMPORT_TOTAL_MD_BYTES = 20 * 1024 * 1024  # 20 MB uncompressed across all members

Then in _parse_zip_entries, cap the member count and check the declared size before decompressing, reading through a bounded stream:

    infos = zf.infolist()
    if len(infos) > _MAX_IMPORT_ZIP_ENTRIES:
        raise HTTPException(status_code=413, detail="ZIP must contain ≤ 500 files")

    entries: list[tuple[str, str]] = []
    total_bytes = 0
    for info in infos:
        if info.is_dir() or not info.filename.lower().endswith(".md"):
            continue
        # Prevent path traversal — keep only the bare filename
        safe_name = Path(info.filename).name
        if not safe_name:
            continue
        # Reject on the declared uncompressed size *before* decompressing, so a
        # compression bomb cannot allocate gigabytes ahead of the size check.
        if info.file_size > _MAX_IMPORT_MD_BYTES:
            raise HTTPException(status_code=413, detail=f"{safe_name} exceeds 1 MB limit")
        total_bytes += info.file_size
        if total_bytes > _MAX_IMPORT_TOTAL_MD_BYTES:
            raise HTTPException(status_code=413, detail="ZIP contents exceed 20 MB uncompressed")
        # Read one byte past the cap so a lying central-directory header cannot
        # beat the check above.
        with zf.open(info) as fh:
            md_bytes = fh.read(_MAX_IMPORT_MD_BYTES + 1)
        if len(md_bytes) > _MAX_IMPORT_MD_BYTES:
            raise HTTPException(status_code=413, detail=f"{safe_name} exceeds 1 MB limit")
        title = Path(safe_name).stem or _DEFAULT_IMPORT_TITLE
        entries.append((title, md_bytes.decode("utf-8", errors="replace")))

The bounded zf.open(...).read(cap + 1) is load-bearing rather than defensive extra: info.file_size is attacker-declared, so a header claiming 100 bytes over a 10 GB deflate stream would pass a file_size-only test. Verified under tracemalloc that this form peaks at 2.6 MB where zf.read peaked at 601 MB. 413 with a "≤" detail string matches the existing style at lines 81 and 112. Worth adding a test at apps/backend/tests/api/test_docs.py asserting POST /api/v1/docs/import returns 413 for a deflate bomb, since the endpoint currently has no tests at all.

### B06 — IPAM network scan materialises the full host list before the size check — unbounded hang on IPv6, multi-GB spike on IPv4

**Location:** `apps/backend/src/app/api/ipam.py:207`  ·  **Severity:** HIGH  ·  **Hunt id:** `F06`

Test the O(1) integer `num_addresses` before expanding the generator, retaining the existing `len` check so the accept/reject boundary is bit-for-bit unchanged (an IPv4 /22 has num_addresses 1024 / 1022 hosts, so nothing currently accepted becomes rejected). Replace lines 207-209 with:

    if network.num_addresses > 1024:

This caps materialisation at 1024 address objects for any input. Add a regression test asserting that POST /api/v1/ipam/scan/{id} on a network whose cidr is "2001:db8::/32" returns 400 promptly.

### B08 — get_redis() treats Redis pool exhaustion as a dead server and calls aclose(), disconnecting every live pub/sub socket in the process

**Location:** `apps/backend/src/app/core/redis.py:84`  ·  **Severity:** HIGH  ·  **Hunt id:** `F08`

Two changes in apps/backend/src/app/core/redis.py.

1. Never let a local resource shortage disconnect healthy connections. Add the import and a dedicated branch ahead of the generic one in `get_redis()`:

    from redis.exceptions import MaxConnectionsError

    if _redis is not None:
        try:
            await cast(Awaitable[Any], _redis.ping())
            return _redis
        except MaxConnectionsError:
            # Pool exhaustion is a local shortage, not a dead server. aclose()
            # here would call pool.disconnect(), severing every in-use
            # connection — including the pub/sub socket each WS listener holds
            # for the life of its connection. Degrade this one call instead.
            _logger.warning(
                "Redis pool exhausted (max_connections=%d) — degrading this call",
                _MAX_CONNECTIONS,
            )
            return None
        except Exception:

This is the whole fix. Nothing depends on the current wording: no test asserts the prompt text, and docs/installation/uninstalling.md:87 says only "with confirmation". Leave the image/Caddy/CA prompts (121, 189, 212) as `[Y/n]` — they are recoverable (re-pull, re-run install) and flipping them would make the uninstaller tedious for its actual purpose. Do not add a typed-name confirmation here; `cb restore`'s "Type RESTORE" (cb:604) belongs to a command that overwrites a live install, whereas this prompt is an offer to spare data during an already-requested removal, and the [y/N] default carries the same protection at a fraction of the friction.

### B38 through B50 — the short entries

Each was found by an agent working a different finding, reported rather than fixed
(fixing outside the assigned scope is how a remediation pass stops being reviewable), and
each carries the reporter's own reasoning. The one-line statements in the table above are
the finding; what follows is only what a reader needs to act.

**B38** is B05 one frame up. `_parse_zip_entries` checks `len(data)` and answers 413, but
`await file.read()` at the top of the handler already pulled the whole body into one
`bytes`. Starlette spools past 1 MB to disk, so the body is not held in RAM while it
streams — but an unparameterized `.read()` materialises all of it at once. Mitigated in
the shipped topology by `client_max_body_size 10m`; not mitigated for anything reaching
the ASGI app directly. Fix: `await file.read(_MAX_IMPORT_ZIP_BYTES + 1)`.

**B39** is the same class as B31 on a distinct code path, and is listed as R2 above
because the B31 fix makes it the last disagreeing copy. Under CSP Level 3 `strict-dynamic`
makes the browser ignore `'self'` and every host source; with no nonce and no hash that
policy permits no script whatsoever. `main.py` registers `spa_fallback` whenever a `dist`
directory exists, and the mono image sets `STATIC_DIR=/app/frontend/dist`, so the route is
registered in the shipped container. Neither shipped deployment routes browsers through
it — which is why this is MEDIUM — but `docs/deployment-security.md:184-200` explicitly
contemplates fronting the backend with a proxy that sets no CSP of its own.

**B40** was flagged by the hunt itself as a follow-up to B19 and is recorded here so it is
not lost: making the pre-upgrade dump *honest* (B19) did not make it *restorable*.

**B43**: both registrations wrap the same callable on the same trigger under different
ids, and `SingleOwnerScheduler` keys its advisory lock on the job id — so the two do not
exclude each other, and `reload_discovery_jobs` only ever removes one of them. Low impact
(a bounded DELETE run twice) but it defeats the SRV-02 single-owner guarantee that the
id-keyed lock exists to provide.

**B44** deserves a deliberate decision rather than a patch. A repo-wide grep for
`discovery.jobs` returns three hits, all inside `discovery.py` itself: the `add_stream`,
the subscribe, and a log line. Either the publisher was lost in a refactor — in which case
scheduled discovery is silently not running through this path — or the worker is vestigial
and should be removed along with its stream. It currently runs a full container and
appears live in `topology.py`.

**B46** is not a request to default the prompts. The safety behaviour (nothing is deleted
without an answer) is correct and load-bearing. The defect is that the abort happens
*after* the container is stopped and removed, with no message, so the operator is left
half-uninstalled with an exit code they may not see through a pipe. The honest fix is a
`[ -t 0 ] || [ -r /dev/tty ]` preflight that fails before touching anything, or an
explicit non-interactive flag — a decision about the script's contract, not a defect fix.

### B36 — The bootstrap race test leaves a rotated vault key hash committed

**Location:** `apps/backend/tests/test_bootstrap_security.py:207`  ·  **Severity:** HIGH

`test_concurrent_bootstrap_requests_create_exactly_one_first_admin` drives
`auth_service.bootstrap_initialize` on committed `SessionLocal()` sessions rather than on
the rolled-back `db_session` fixture, because the point of the test is a real two-thread
race. `bootstrap_initialize` calls `_generate_and_persist_vault_key`
(`services/auth_service.py:585`), which mints a fresh key and commits its SHA-256 to
`app_settings.vault_key_hash`.

The test's cleanup block puts back `auth_enabled` and deletes the users it created. It
does not put back the vault key columns. Every test that runs afterwards in the same
session sees an `app_settings.vault_key_hash` that no longer matches the process
`CB_VAULT_KEY` that `conftest.pytest_configure` set — which is exactly the stale-key
condition `validate_config` exists to report. So
`tests/test_config_validate.py::test_the_database_tier_supplies_the_jwt_secret_and_names_itself`
fails, ~1300 tests away from the test that caused it.

This is why it was invisible: both files pass in isolation, and the backend suite's
`addopts` carries `-x`, so the run stops at the first failure and never reaches the rest.

Reproduce:

    cd apps/backend && PYTHONPATH=src pytest \
      tests/test_bootstrap_security.py tests/test_config_validate.py \
      -q --no-cov -p no:randomly

**Fix (working tree):** captures `vault_key`, `vault_key_hash` and `vault_key_rotated_at`
before the race and restores them in the same committed transaction the existing cleanup
uses. Verified by watching the two-file reproduction above fail, then pass.

### B37 — The backend suite writes a real vault key into the working tree

**Location:** `apps/backend/tests/conftest.py:29`  ·  **Severity:** MEDIUM

`vault_service._DATA_ENV_PATH` is computed **at import time**
(`_DATA_ENV_PATH = _get_data_dir() / ".env"`, `vault_service.py:37`), so it resolves
against whatever `CB_DATA_DIR` held when the module was first imported. `conftest`
redirects `UPLOADS_DIR` in `pytest_configure` for precisely this reason — and explains at
length why a fixture-time monkeypatch would be too late — but does not redirect
`CB_DATA_DIR`.

Two consequences:

1. `write_vault_key_to_env` deposits a real Fernet key at `apps/backend/data/.env` (0600)
   on every run that bootstraps. It is gitignored, so it does not show up in review, but
   it is live secret material written outside any temp dir, and `load_vault_key` reads
   that same path — so one run can influence the next.
2. The three tests that *do* `monkeypatch.setenv("CB_DATA_DIR", str(tmp_path))`
   (`test_bootstrap_security.py:95,142,170`) are not actually redirecting the env write,
   for the import-time reason above. They pass regardless, which is the more
   uncomfortable half.

**Fix:** set `CB_DATA_DIR` to a per-run `mkdtemp` in `pytest_configure` beside the
existing `UPLOADS_DIR` redirect, and remove it in `pytest_unconfigure`.
