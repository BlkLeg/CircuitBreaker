# Codebase Gap Audit vs. the 1.0.0 Production-Readiness Plan

**Date:** 2026-08-18
**Auditor:** Claude (session notes)
**Tree audited:** branch `dev` @ `afbd382b`, `VERSION` = `1.0.0-rc.2`
**Plan audited against:** `specs/1.0.0/` (9 normative specs, 145 requirement IDs)

> This is a **gap note, not release evidence**. Nothing here satisfies the shared definition of
> done in `specs/1.0.0/README.md`. Its purpose is to record where the tree stands against the
> plan, and — where the ledger and the code disagree — which one is right.

## Headline

The ledger (`release-control/requirement-ledger.csv`) is broadly honest: 125/145 `not_started`,
9 `in_progress`, 8 `passed`, 3 `excepted`. Spot-checking the code confirms the shape of that
picture. **Security (SEC) is the only workstream with real depth.** AGT, SRV, ACC, REL, GOV, NPM
and EXEC are close to greenfield, and three of the plan's named defects (AGT-10/11/12) are
verifiably still present in the tree.

Two findings below are worse than the ledger implies, because they are *contradictions* rather
than absences: the published support contract claims arm64 for the container channel that CI
cannot build, and `:latest` is promoted unconditionally at release time.

---

## A. Contradictions — the shipped tree disagrees with the published contract

### A1. `docs/release/1.0.0-support-contract.md:40` claims arm64 Docker; the release pipeline builds amd64-only

`build.yml:22-30` builds native packages on a real `ubuntu-22.04` + `ubuntu-22.04-arm` matrix, so
deb/rpm/apk/Arch/AppImage/tar are genuinely dual-arch. The **container** is not: `release.yml:47`
runs the publish job on `ubuntu-22.04` and `release.yml:100-106` uses a plain `docker build` with
no `buildx`, no `--platform`, and no QEMU step. The image pushed to
`ghcr.io/blkleg/circuitbreaker` — including `:latest` — is amd64-only.

The support contract row "Docker Compose install → Linux `amd64` and `arm64`" is therefore an
untested-and-unbuildable claim, which is precisely what RC-02 forbids ("no untested row is called
supported"). Affects **RC-02, ACC-17, GOV-19**.

### A2. `:latest` is promoted before any acceptance, including for release candidates

`release.yml:100-106` tags and pushes `${VERSION}` and `latest` in the same step, and
`release.yml:207-221` creates the GitHub Release with no `--prerelease` flag. Tagging `v1.0.0-rc.3`
today would move the Docker `latest` channel and the GitHub "Latest release" badge to a release
candidate, with zero installed-artifact gate in between.

GOV-20 requires promotion to be "an explicit post-acceptance action". Nothing in the pipeline
installs a built package on a clean host before publication. Affects **GOV-20, ACC-17, EXEC-07**.

### A3. Two divergent `cb` CLIs ship, and only one is documented

| | `./cb` (repo root, 416 lines) | `deploy/cli/cb` (installed by `deploy/setup.sh:1227`) |
|---|---|---|
| Modes | docker / compose / binary | native systemd |
| Commands | status, logs, restart, update, **vault-recover**, version, uninstall | status, **doctor**, logs, restart, update, **backup**, version, uninstall |

`docs/cb-cli.md` documents the second one only. A user on the docker install path gets a `cb` with
no `doctor` and no `backup`, following docs that describe both. Affects **SRV-06, GOV-05, GOV-07**.

### A4. Single-tenant contract, but tenant-shaped strings and query args survive

ADR-0003 + `api/tenants.py` (410 Gone) + `middleware/tenant_middleware.py` (ContextVar always
`None`) + `context/TenantContext.jsx` (inert provider) are a genuinely good SEC-05 implementation.
Residue that still contradicts it in user-visible surface and code:

- `components/monitors/RunFromSelect.jsx:20` and `components/discovery/ScanProfileForm.jsx:69`
  render the error text *"the agent belongs to a different tenant"* to operators.

~~`api/graph.py:1111` still threads `getattr(user, "tenant_id", None)` into the graph query
path.~~ **Retracted 2026-08-18.** This is correct code, not a remnant. `User` *does* carry
`tenant_id` (`db/models.py:1967`), and `monitor_service.reader_can_access_monitor` uses it
deliberately: v1 is single-tenant, but *upgraded* data can still carry legacy tenant ids, so a
monitor is hidden only when reader and target both have ids and they differ. The topology body is
therefore reader-dependent (`graph.py:405-406`), which is exactly why `reader_tenant_id` belongs in
the ETag key — without it a revalidating cache could answer one reader with another's body.
`tests/api/test_monitor_read_side_channels.py` exists because "the map handed out rollups for
targets belonging to another tenant" was a real SEC-08 bug that this code fixed. Removing it would
reintroduce it.

Affects **SEC-05** (ledger: `in_progress` — correct, and these are the remaining items).

## B. Named defects from the plan that are still live in the tree

### B1. AGT-12 — string environment name reaches an integer API field (**confirmed reproducible**)

`pages/MapPage.jsx:646-652` writes `settings.default_environment` — a **name string** — straight
into `envFilter`, behind a `settingsApplied.current` once-only guard. The inline comment says
*"will be reconciled after environmentsList loads"*, but no reconciliation exists:
`environmentsList` is referenced only at its declaration (`:386`), the comment (`:651`), and the
`<option>` render (`:1857`).

That value then flows to the API as `environment_id`:

- `pages/MapPage.jsx:874`
- `hooks/useMapDataLoad.js:173` (and `:119`, `graphApi.placeNode(newNodeId, envFilter || 'default')`)
- `components/map/SigmaMap.jsx:79`

The receiving signature is `api/graph.py:1105` → `environment_id: int | None = Query(None)`. A
configured default environment therefore 422s the map on load. AGT-12's acceptance ("no string
reaches the integer API field") is unmet, and none of its five required test cases exist.

### B2. AGT-11 — `--onefile` PyInstaller with no owned extraction directory

`scripts/build_native_release.py:195` passes `--onefile` with no `--runtime-tmpdir` and no
application-owned extraction path. Nothing in `scripts/`, `packaging/`, or `deploy/` references
`_MEI`, `MEIPASS`, or a cleanup of stale Circuit Breaker extraction state. The unbounded `_MEI*`
accumulation AGT-11 exists to fix is unaddressed.

### B3. AGT-10 — no evidence the ARM64 Pillow/AVIF crash was resolved

`Pillow>=12.3.0` (`apps/backend/pyproject.toml:31`) with no upper bound. Repo-wide grep for
`avif`/`AVIF` across `*.py`, `*.spec`, `*.sh`, `*.toml` returns **nothing** — no exclusion, no
replacement, no hidden-import handling, no regression test.

**Partially corrected 2026-08-18.** The *upload* surface was less exposed than this implied:
`auth_service._ALLOWED_TYPES` already limited avatars to `image/{jpeg,png,gif,webp}` by magic-byte
sniffing, and `_PILLOW_FORMAT_TO_MIME` re-checked the decoded format. AVIF could not actually be
uploaded. But those were **three independent literals that happened to agree**, with no test tying
them together, and `_process_avatar` took `probe.format` unchecked — so the accepted set tracked
whatever the installed Pillow wheel had compiled in. Verified locally: Pillow 12.3.0 reports
`features.check("avif") == True`, so the plugin is live wherever it is built.

What was genuinely missing, and is what AGT-10 asks for: a named policy, and any assertion that the
supported formats round-trip **on the running architecture** — so the arm64 CI job proves the arm64
claim instead of a comment asserting it.

### B4. AGT-04 — the uninstall xfail is still open, but its stated reason is stale

**Corrected 2026-08-18.** This entry originally reported that the xfail named three unfixed
production bugs. On verification it does not: all three were fixed *after* the marker was written,
and nobody removed it.

`apps/agent/e2e/test_agent_e2e.py:1275` is a live `xfail(strict=False)` — the only one in the repo.
Its reason text names three defects. Each is fixed in the current tree:

| Bug named in the xfail | Current state | Fixed in |
|---|---|---|
| `link.go` `Uninstall()` reads one frame while the server sends two (`hello.ack` + `capabilities.set`) — RST-on-close data loss | `drainPending()` loops until error, after a real WS close handshake (`link.go:1056-1061`) | `4aab49d5` |
| `ws_agents.py` `link_stream` swallows frame-decrypt failures with a bare `except Exception: continue` | Logs `agent %s: dropped undecryptable inbound /link frame` with the exception (`ws_agents.py:836`) | `4aab49d5` |
| `agent_registry` deregister kills a second, still-live connection — cross-worker presence corruption | Atomic compare-and-delete Lua scoped to `worker_id`, with the race documented (`agent_registry.py:1283-1302`) | `ad197961` |

Commit ordering confirms it: the marker landed in `6903d6db` at 14:42 on 2026-08-05; the fixes
landed at 16:53 the same day. Because `strict=False`, a now-passing test reports as `xpass` and
nobody notices.

The remaining work is therefore verification and deletion, not repair — RC-08 forbids an
unexplained xfail at sign-off, and this is the repo's only one.

### B5. `known_bugs-v1.0.0-rc.1.md` item 1 — open high-severity navigation regression

Clicking a nav entry changes the URL but not the rendered page until a manual reload; open in rc.2.
The file's own analysis is the point: *"A jsdom test cannot catch this class of bug, which is a
large part of why it regressed unnoticed."* This is REL-17's exact justification, and REL-17 does
not exist (see C3).

## C. Whole workstreams with no implementation

### C1. No browser/E2E layer at all (**ACC-09, ACC-10, REL-17, REL-18, AGT-13, AGT-17**)

No `playwright.config.*` anywhere in the tree. No visual-regression baselines. No accessibility
automation. The only `e2e/` directory is `apps/agent/e2e` (a Python/Docker agent journey, not a
browser suite). Every browser-facing acceptance row in the plan — including AGT-13's "browser E2E
proves the resulting monitor targets the imported hardware through that agent" — has no harness.

### C2. The composed agent journey is not a release gate (**AGT-01, AGT-02, AGT-03**)

`apps/agent/e2e/test_agent_e2e.py` is a substantial suite, but `ci.yml:104` and `dev-ci.yml:77`
both state it is *"deliberately NOT run here and remains a local/manual gate"*, and `release.yml`
never invokes it. AGT-01 requires it to run "against every RC and on a schedule" as a required
workflow with retained logs/traces/timing/seed.

### C3. No performance, capacity, or soak measurement (**REL-21 – REL-26, RC-05, RC-06, SRV-07**)

The only benchmark in the tree is `scripts/bench-topology.py` (topology graph builder,
`<50ms @ 10k nodes`). Nothing for concurrent agents (REL-22), mixed workload (REL-23), frontend
budgets (REL-24), or 24h/7d soaks (REL-25). No `soak` harness exists — the string appears only in
`specs/`. Consequently every published limit in `docs/release/1.0.0-service-objectives.md` (24h
RPO / 4h RTO) is a target with no measurement behind it.

### C4. No support bundle, dashboards, or alert examples (**SRV-09, ACC-11**)

`support_bundle` / "support bundle" appears **only in `specs/`** — zero implementation. No Grafana
dashboard JSON, no Prometheus alert rules. `api/metrics.py` exposes inventory-count gauges only:
no queue lag, job duration, worker lease, or agent-fan-out metrics, and no cardinality/redaction
schema test.

### C5. No npm package (**NPM-01 – NPM-15**)

Only two tracked manifests: root `package.json` (correctly `private: true`) and
`apps/frontend/package.json`. No dedicated `@blkleg/*` package, no publish workflow (grep for
`npm publish` / `NODE_AUTH_TOKEN` across `.github/workflows/` returns nothing). NPM-01's product
decision is unmade, so the whole spec is either 15 open requirements or one "out of scope for 1.0"
ADR. **The cheapest release-scope win available.**

### C6. Health is one endpoint doing four jobs (**SRV-03, RC-05**)

`main.py:1941` is the only health route in the app. It returns `state`, `ready`, `uptime_s`, and
`checks.{db,redis}` from a single `GET/HEAD /api/v1/health`. There is no distinct liveness,
startup, or readiness endpoint, no dependency-fault matrix, and nothing that makes readiness
*reject writes* when they cannot be served safely. SRV-03 requires all four to be distinguishable.

### C7. No config validation surface (**SRV-05**)

`cb config validate` does not exist — grep for `config validate` / `config_validate` across the
whole tree returns nothing. `deploy/scripts/validate-secrets.sh` covers secrets only, not
precedence conflicts across file/env/database/CLI.

## F. What is genuinely in good shape

Worth recording so it does not get re-done:

- **Security scanning (SEC-18)** — `scripts/security_scan.sh` runs 11 scanner stages; `security.yml`
  + `codeql.yml` cover Trivy fs/config, Semgrep, Bandit, Gitleaks, govulncheck, CodeQL (Python +
  JS). `release.yml:113-131` scans the **built image by digest** before cosign signs it, with a
  documented, non-cosmetic rationale for its severity gate. `validate_security_suppressions.py`
  enforces suppression metadata.
- **Supply chain (GOV-19, partial)** — syft SBOMs (CycloneDX + SPDX), cosign keyless signing, SBOM
  attached to the image, GPG-signed `SHA256SUMS`. Missing only SLSA provenance attestation.
- **Tenancy removal (SEC-05)** — clean and deliberate; the 410-Gone legacy route with a rationale
  comment is the right call, not a deletion.
- **Endpoint policy inventory (SEC-06)** — `security/endpoint_inventory.json` +
  `scripts/generate_endpoint_inventory.py` + `tests/test_endpoint_policy_inventory.py`, with the
  FastAPI upper bound in `pyproject.toml:16-19` pinned *because* a newer version silently collapses
  the route walk from 428 routes to 4. That comment is the kind of thing that saves a release.
- **Release control** — `scripts/validate_v1_release_control.py` passes (145 rows, 145 canonical
  IDs). ⚠️ But **it is not wired into any CI workflow**, so the ledger can drift silently.
- **Worker/lease infrastructure** — dedicated `workers/` package, per-worker systemd units
  (`circuitbreaker-worker@.service`), advisory locks and leases in the scheduler/dispatch paths.
  SRV-02's *implementation* is largely present; its *multi-process proof* is not.
- **Migrations** — 109 revisions, single head, verified in CI (`ci.yml:33`).
- **Backup/restore** — `services/backup/` (snapshot, pruner, s3_client), `deploy/scripts/restore.sh`
  with manifest + SHA256 verification, and honest docs distinguishing JSON export from full-state
  snapshot. ACC-14/15's *failure-mode* testing is what is missing, not the feature.

## G. Suggested order of attack

1. **A1 and A2 first.** They are contradictions, not absences — the product currently makes claims
   the pipeline cannot honor, and `latest` can be moved to an RC by a single tag push. Both are
   small, mechanical fixes (buildx + a promotion gate + `--prerelease`).
2. **B1 (AGT-12).** Confirmed reproducible, user-visible, and a ~20-line fix plus the five tests
   AGT-12 already names.
3. **C5 (npm).** One ADR declaring npm out of 1.0 scope closes 15 requirements. If it stays in
   scope it is a whole workstream — decide before it costs anything.
4. **C1/REL-17.** Playwright is the prerequisite for six ACC/REL/AGT rows *and* is the only thing
   that would have caught the open rc.2 navigation regression. Highest leverage per hour.
5. **E (GOV hygiene).** `git rm` the junk, add `SECURITY.md`, delete the Poetry block, pin the
   build tools, wire `validate_v1_release_control.py` into CI. A few hours, closes many rows.
6. **The agent docs page.** Cheapest way to stop shipping an undocumented headline feature.
