# Circuit Breaker 0.4.7 — npm CLI implementation plan

Date: 2026-09-30. Status: **Active — planned; no implementation task started.**

The [design contract](../docs/design/2026-09-30-v0.4.7-npm-cli-design.md)
controls product behavior and presentation. Its [preview gallery](../docs/design/assets/cli-0.4.7/README.md)
records the approved visual pattern. This plan turns that contract into reviewable
implementation slices; it is not evidence of a working or published CLI.

[ADR 0006](../docs/adr/0006-npm-installer-cli-for-1.0.md) controls distribution,
namespace, trust and publication. The [npm requirements](../specs/1.0.0/08-npm-distribution.md)
and [existing slices](../specs/1.0.0/08-npm-distribution-implementation.md)
remain the requirement baseline. Their older product-decision blockers and SDK
branch do not override the accepted ADR. Record actual evidence in the requirement
ledger only when the corresponding checks pass.

## Deliverable and boundaries

Release one Linux management/installer package, `@blkleg/circuitbreaker`, in
lockstep with 0.4.7. Carry every native management command and add explicit install,
update, downgrade, rollback, history, recover and CLI-only update. Keep the native
shell installation path, its existing artwork and useful installer logic.

The npm binary is `circuitbreaker`; installed hosts keep `/usr/local/bin/cb`.
Native `cb` forwards new lifecycle operations to a recorded, validated absolute
launcher with a recursion guard. Fresh hosts use the npm binary until installation
creates the native `cb`. Do not add npm hooks that download, elevate or modify the
server. The root and frontend manifests stay private. An SDK and non-Linux support
are outside this release.

Native lifecycle support is the first adapter. Add Docker lifecycle support using
recorded identity, immutable images and volume recovery before claiming that mode.
Package-owned installs stay with their package manager. Proxmox mutations run
inside the identified guest. Untested modes receive an actionable refusal before
mutation; everyday management retains existing supported adapters.

All proposed new paths below are implementation targets, not existing files.

## 1. Freeze executable contracts and supported transitions

Dependencies: none. Requirements: NPM-01–03, NPM-08, NPM-11.

- [ ] Add versioned schemas under `packages/cli/schemas/` for release/compatibility
  metadata, lifecycle plans, events, results and operation journals.
- [ ] Derive a command inventory from `cb`, including nested commands, options,
  streaming behavior, native exit codes and JSON contracts. Add parser/bridge
  acceptance cases for every entry, including argument values containing shell syntax.
- [ ] Specify plan fields: operation/action, source/target versions and digests,
  identity, adapter, schema compatibility, downtime, recovery reference, data impact,
  trust result and required acknowledgments. Bind a canonical plan digest to execution.
- [ ] Select and test the Node/architecture/distro matrix against release CI.
  Encode only tested combinations in package metadata; report unsupported hosts early.
- [ ] Audit one real older release for a certified downgrade journey. Bind explicit
  source/target schema transitions and artifact digests to signed compatibility
  metadata. Missing historical trust metadata is a refusal unless independently
  certified through the approved trust process; never disable verification.
- [ ] Keep post-1.0 downgrade restrictions intact. Record which 0.4.x transitions
  preserve data and which require an exact matching recovery point.

Exit: schemas and command/transition fixtures are reviewable; no historical version
is declared compatible merely because its version number is lower.

## 2. Establish the package and native bridge

Dependencies: 1. Requirements: NPM-02, NPM-05–07, NPM-10–11.

- [ ] Create `packages/cli/package.json`, its lockfile, `bin/circuitbreaker.js` and
  `src/` modules for commands, identity, bridge, releases, lifecycle and rendering.
  Prefer a small dependency surface; record any verifier/runtime dependency in SBOM.
- [ ] Add a strict runtime/license/documentation/trust/schema file allowlist, explicit
  size/file-count budgets and packed-tarball inspection. Exclude server/frontend
  payloads, design exports, environment files, credentials and secret fixtures.
- [ ] Read `specs/install/identity.schema.json` through a validated identity adapter.
  Resolve native paths from trusted install metadata; never search arbitrary PATH
  for `cb`, guess ports/containers, or evaluate command strings.
- [ ] Modify `cb` and synchronize `deploy/cli/cb` byte for byte. Register optional npm
  launcher metadata without requiring Node for existing shell management.
  Validate launcher ownership/context; never execute a user-writable Node launcher
  as root. Delegate privileged work to the native helper instead.
- [ ] Implement help, version and management forwarding with argument arrays,
  inherited streams/signals and the recursion guard. Help/version/status perform
  no automatic network checks. Report CLI and server versions separately.
- [ ] Register CLI manifests/lockfile in `scripts/check_version_parity.py` and
  `scripts/post_release_bump.py` when introduced. Do not bump VERSION during planning.

Exit: installing the exact packed package creates only the npm tool; command parity
and native operation without Node pass on disposable hosts.

## 3. Implement immutable staging and verification

Dependencies: 1–2. Requirements: NPM-03, NPM-09–10.

- [ ] Resolve release/channel once to an immutable target and platform artifact.
  Implement bounded downloads, proxy settings, size/space limits, timeouts, capped
  retries and safe resume tied to the same immutable identity.
- [ ] Verify digest, signature and provenance against pinned trust and expected
  repository, workflow, tag and platform. Verify the installer executable as well.
  Define offline trust material and key rotation; checksum alone is insufficient.
- [ ] Validate archive paths, symlinks and resource limits before extraction.
  Finalize staging atomically in private storage. Reverify completed resumed files.
- [ ] Honor `CB_AIRGAP=true`, `--airgap` and `--local-bundle`; the full verification
  set must be local. Air-gap planning, verification and execution make zero requests.
- [ ] Add a target-bound local-bundle path to `install.sh`/`deploy/setup.sh` that
  prevents independent mutable downloads and rejects npm trust bypass flags.
- [ ] Run only the native mutation helper under elevation. It independently validates
  ownership, staged bytes, identity and plan digest before changing the host.
  Copy accepted inputs to root-controlled storage to prevent verification/use races.

Exit: corrupt, substituted, unsigned, wrong-provenance and traversing artifacts
fail before service stop or privileged installation changes.

## 4. Build shared locking, journals and lifecycle events

Dependencies: 1–3.

- [ ] Add shared native lifecycle utilities under `deploy/lib/`: an install-scoped
  exclusive lock, atomic restricted journals and a versioned event descriptor.
  Apply the lock to npm and direct shell lifecycle paths, including restore/removal.
- [ ] Keep state root-owned and outside npm caches. Reject unsafe owners, symlinks
  and conflicting operations. Read-only history exposes redacted summaries.
- [ ] Persist phases: planned, staged, verified, recovery saved, applying, checking,
  committed, recovering, recovered, recovery required and interrupted. Preserve the
  last durable checkpoint before acknowledging a transition.
- [ ] Event envelopes contain schema version, operation ID, sequence, timestamp,
  phase/state, measured progress units and safe detail. Never include credentials.
  Dedicated descriptor events do not mix with command stdout or JSON results.
- [ ] `--json` yields one final result; `--events=jsonl` yields an explicitly separate
  event stream. Define stream destinations in help and test them. Preserve forwarded
  JSON schemas and use the lifecycle exit-code table in the design.
- [ ] Signals request safe checkpoints; process death leaves discoverable state.
  Retention never deletes the sole recovery point for an unfinished operation.

Exit: competing shell/npm runs cannot overlap; kill/restart tests reconcile durable
state rather than trusting the last printed phase.

## 5. Complete native backup and restore adapters

Dependencies: 2, 4.

- [ ] Route native `cmd_backup` and `cmd_restore` through the shared snapshot/restore
  implementation in `apps/backend/src/app/services/backup/` and
  `deploy/scripts/restore.sh`; keep both CLI copies synchronized.
- [ ] Preserve private snapshot creation, atomic finalization and failed-partial
  cleanup. Verify archive structure and compressed database checksum before use.
- [ ] Fix `deploy/setup.sh:run_upgrade` so inactive PgBouncer never skips backup.
  Test actual database connectivity through the supported backup connection.
  A failed or unavailable database backup blocks activation.
- [ ] Extend lifecycle recovery beyond data snapshots: old executable/release tree,
  units, configuration, identity, database, uploads and vault key. Record digests,
  schema and timestamps; protect secrets from creation, not with a late chmod.
- [ ] For lifecycle operations quiesce application writes and drain workers before
  the database/uploads recovery snapshot. Ordinary online backups must not claim
  globally consistent cross-resource capture unless that is actually enforced.
- [ ] Retain the existing restore safety snapshot requirement. Add full disposable
  restore rehearsals; archive verification alone is not a successful restore.
- [ ] Preserve `--encrypt-to` semantics: an additional age derivative does not remove
  the local plaintext snapshot; off-host restore needs an independent age identity.

Exit: restore reproduces data, uploads, vault decryption, configuration and old
release state; backup failure cannot fall through to upgrade.

## 6. Implement install/update and the health commit boundary

Dependencies: 3–5.

- [ ] Implement plan/confirmation and native apply through the verified existing
  installer core. Preserve explicit port/FQDN/TLS/email/data-dir/Docker options.
  Existing installs direct `install` to update; same-version update is a no-op.
- [ ] Stage replacement files before stopping services. Track every changed file,
  unit and dependency action so recovery can reconcile partial activation.
- [ ] Add a maintenance/write gate at the backend and workers. Keep external writes
  blocked from recovery capture through activation checks and durable commit;
  readiness alone does not currently provide this gate. Include bypass/background
  write paths in tests and expose actual maintenance state to diagnostics.
- [ ] Require bounded readiness, expected version/schema and matching identity.
  Durably commit the operation before reopening writes. Recover a crash between
  commit and gate release by reconciling actual state.
- [ ] On failure recover only to a verified preauthorized point when writes are
  accounted for. Report attempted target and resulting version; recovered failure
  exits 8, failed/unsafe recovery exits 9 and retains artifacts.

Exit: install/update journeys and injected activation/migration/health failures
produce accurate outcomes with a proven recovery path.

## 7. Implement downgrade, rollback, recover and CLI-only update

Dependencies: 1, 4–6.

- [ ] Compatible downgrade snapshots current state and retains current data.
  Incompatible downgrade requires the matching recovery point, visible loss window
  and explicit restore acknowledgment. No matching point means pre-mutation refusal.
- [ ] `rollback` selects a retained operation and shows its actual release/data impact;
  capture current state before replacement. Do not treat `.prev` binaries as recovery.
- [ ] `recover` reconciles files, units, identity and actual schema. Never blindly
  retry interrupted migrations. Offer only safe resume/recovery actions.
- [ ] Distinguish read-only inspection from confirmed recovery. Preserve the explicit
  `--restore-data` requirement for unattended data replacement.
- [ ] CLI-only update uses recorded npm ownership/install context without server
  mutation. Unknown contexts print applicable manual instructions; never sudo npm.

Exit: real certified older-release downgrade, incompatible refusal, explicit data
restore, retained-point rollback and interrupted-operation recovery journeys pass.

## 8. Implement uninstall and purge

Dependencies: 4–5.

- [ ] Reuse `uninstall.sh` under the shared lock. Present identity-derived removal
  paths and retained configuration/database/uploads/vault key/backups before stop.
- [ ] Default npm removal retains data and the npm tool. Preserve shared dependencies.
  Purge is an explicit choice, with interactive `DELETE circuitbreaker` confirmation
  entered into an initially empty prompt before any service stop.
- [ ] Unattended purge requires explicit purge selection, the exact deletion scope
  and a separate documented deletion acknowledgment. Generic `--yes` is insufficient.
  Preserve existing direct-shell flag semantics while documenting adapter behavior.
- [ ] Resolve/validate deletion paths under privilege; reject unsafe roots and
  symlink substitutions. Interrupted removal reports actual remaining state.

Exit: keep-data reinstall retains decryptable state; cancelled purge changes nothing;
confirmed purge removes only its declared scope.

## 9. Implement the approved terminal surfaces

Dependencies: 2, 4; lifecycle screens also require 5–8.

- [ ] Implement the common event/presentation contract in npm and standalone shell
  renderers. Only one renderer owns a terminal per operation. Keep `cb_logo` byte
  identical; synchronize the inline installer fallback with
  `scripts/ci/sync_installer_ui.py` after edits to `deploy/lib/ui.sh`.
- [ ] Render permanent completed phases, a bounded live region, measured download
  progress and elapsed-time spinners for unknown work. Cap redraw at 8 Hz; final
  operation success requires health. Support resize, narrow layouts, no color,
  static motion, Unicode fallback, redirected output and cursor restoration.
- [ ] Implement grouped `cb` help and compact routine headings. Restyle native
  resources output in `deploy/cli/cb_resources.py` without changing accounting/JSON:
  seven real workers, cache-inclusive memory, separate swap, unavailable as null,
  shared services excluded from application totals and visible-capacity caveats.
- [ ] Preserve snapshot vs watch behavior and existing keyboard controls. Present
  status process state separately from readiness; doctor remains read-only and
  reports authenticated checks as skipped when credentials are absent.
- [ ] Format interactive logs without dropping/reordering lines or multiline entries.
  Preserve redirected streaming output. Redact lifecycle/support logs at source;
  do not promise arbitrary existing application logs are already secret-free.
- [ ] Match backup completion to real verified artifacts and accurately describe
  plaintext/encrypted outputs. Use all gallery previews as visual acceptance fixtures,
  with illustrative values replaced by real data.

Exit: terminal capture comparisons at wide/narrow sizes and PTY interruption tests
pass; plain/JSON streams contain no ANSI or cosmetic progress contamination.

## 10. Packaged journeys and governed release

Dependencies: all previous slices. Requirements: NPM-05–15.

- [ ] Test the exact `.tgz` on every claimed matrix combination. Exercise complete
  install/manage/backup/update/downgrade/rollback/uninstall journeys on disposable
  hosts, plus proxy, air-gap, permission, trust, storage, interruption and lock failures.
- [ ] Extend existing build tests for banner/UI parity, CLI parity, resource semantics,
  pre-upgrade backup, restore faults and version parity; add behavioral npm journey
  tests rather than relying solely on shell text matching.
- [ ] Revise `tests/build/test_npm_is_not_a_distribution_channel.py` deliberately as
  publication is enabled: allow only the dedicated package and governed release job,
  retain root/frontend privacy and keep premature public instructions forbidden.
- [ ] Integrate `.github/workflows/release.yml`'s candidate build/draft and stable
  promotion flow. Build/sign/scan/attest the CLI tarball alongside server assets;
  promote accepted existing bytes without repacking or rebuilding on tag creation.
- [ ] Configure namespace/MFA/recovery ownership, EXC-005 governance, protected release
  approval and OIDC/provenance. If initial publication needs the ADR's scoped
  short-lived fallback credential, revoke it after trusted publishing is configured.
- [ ] Govern `next` and `latest` promotion. Record npm integrity and server digests in
  release evidence. Cross-registry publication is not atomic: add resumable
  reconciliation, reject mismatched existing versions and withhold stable advertising
  until all required channel gates succeed.
- [ ] Add package/dependencies to SBOM and scans; document compromise, deprecation,
  correction and revocation. Publish user instructions only after registry existence,
  provenance and exact-package acceptance are verified.

Exit: 0.4.7 is available through the governed npm channel with reproducible evidence,
matching versions and automated examples. A checklist or mockup does not close a gate.

## Review and execution order

Land slices 1–5 first to establish contracts, trust and recoverable native primitives.
Then 6–8 implement actual lifecycle behavior. Slice 9 can develop against fixture
events after slice 4, but cannot pass acceptance until real commands supply its data.
Slice 10 is the final release gate. Keep each slice reviewable and attach concrete
validation evidence; leave every unchecked item open until its behavior is proven.

Before starting code, resolve the Node/host matrix and certified older-release target
in slice 1. These are engineering verification tasks, not reasons to restart visual
design. If a transition cannot be certified, record the precise supported boundary
and retain a graceful refusal; do not imply arbitrary downgrade support.
