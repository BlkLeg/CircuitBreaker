# Connection walkthrough

Status: visual design approved 2026-09-29; application implementation pending.
The console/map design is draft `d065afe9-56b1-4c40-b88e-ecb6dd755281`, version 5;
the approved walkthrough is draft `c8e6462a-4db9-44f4-86eb-042aa156bd05`, version 7.
The [approved design record](../docs/design/2026-09-29-map-console-and-connection-walkthrough.md)
contains the visual specification and frozen reference bundle. This document
records the workflow and persistence contract.

## Working flow

1. Choose nodes from the current map's inventory. Search by name, address and
   entity type. Keep stable entity IDs and current native icon/shape metadata.
2. Define connections in a structured diagram. Select source and target, derive
   the supported relationship, and set connection type where that relationship
   actually supports it. Queue additions locally; distinguish existing and
   pending links. Do not remove persisted relationships through queue removal.
3. Review every queued relationship and position change. Preview the result
   using the normal map renderer. **Present Layout** applies reviewed changes
   to the active map and returns to its familiar view.

Rectangular tiles are working representations in the walkthrough only. Native
map node shapes and branded SVGs remain intact. Preserve unaffected nodes,
annotations, boundaries and user edge overrides. A draft preview never changes
the saved map until the reviewed handoff is executed.

## Existing model constraints

`model/linkMutations.js` is the source of truth for relationship mappings and
endpoint support. Its `LINK_ITEMS` table is a first filter, not a sufficient
validation contract: some source pairs also require hosting metadata, and
directional mappings can canonicalize endpoints.

Examples:

| Endpoint pair | Relationship | Connection type persistence |
| --- | --- | --- |
| Hardware → hardware | `connects_to` | Supported |
| Hardware → storage | `has_storage` | Not supported by this mutation |
| Hardware → compute | `hosts` | Not supported by this mutation |
| Service → storage | `uses` | Supported |
| Compute → network | `connects_to` | Supported |

Ownership/hosting mutations can reassign an existing parent. Review must expose
the prior parent and request acknowledgement for that concrete change. The
walkthrough must not describe every operation as an additive link.

Physical/logical connection type uses all twelve current canonical options.
Expose existing endpoint uplink controls with Mbps/Gbps presentation and quick
presets. Effective link bandwidth uses the slower endpoint and the current type
cap. Changing an endpoint's uplink affects its other connections as well; review
must list those endpoint updates separately. This is configured capacity, not
measured traffic. Do not invent a per-link bandwidth write endpoint.

The connection editor also exposes source/target anchor sides (Auto, Top, Right,
Bottom, Left) and reset bend point, carried through existing map edge overrides.
Line color/dashes and particles follow the current `CONNECTION_STYLES` profile;
show them in a live preview without presenting them as existing user-editable
per-link settings. Arbitrary labels, colors, line widths and independent
animation sliders are not current edge customization controls.

## Publication behavior

- Revalidate map identity, edit permission, endpoint existence, current parent
  ownership, existing links and unsaved changes before applying.
- Persist relationships individually using the existing mutation API. Track
  successful changes and refresh authoritative state; do not promise an atomic
  save or rollback.
- If a subset fails, keep the review open, explain which operations succeeded
  and failed, and retry only outstanding operations after revalidation.
- Publish positions only after all reviewed relationship operations succeed.
  If layout saving fails afterward, report that relationships were applied but
  the layout was not saved. Offer a layout-only retry.
- Restore the map view using the same entity IDs and renderer. Handoff must
  preserve live updates, current map membership and document metadata.

## Implementation boundary

New application components, state/types and tests must be TypeScript/TSX.
Design prototypes use illustrative local data and never write to backend APIs.
The approved console is retained alongside this optional walkthrough.
