**Audit date:** 2026-08-23
**Audited revision:** `91944b73` (`dev`), `VERSION` = `1.0.0-rc.3`

**Scope:** Read-only sweep for *incomplete features* — surfaces a user can reach that do not do
what they claim, and implemented backend capability with no way to use it. This is deliberately
narrower than `docs/1.0.0-release-readiness-audit.md` (security/process) and

there are not repeated; see "Already tracked elsewhere" at the end.

plus targeted reads of each subsystem the diff flagged. Every finding below cites source. That
method cannot see a page that is routed, calls its API, and is linked from nowhere — INC-21 is one
such finding, added after the fact.

## P0 — Reachable and wrong

### INC-02. Email notification sink can never deliver

**Resolved.** The sink form collects only `name`, `provider_type`, `webhook_url`, `to`, `enabled`
(`apps/frontend/src/pages/NotificationsPage.jsx`), so an email sink's `provider_config` was
`{webhook_url, to}` — but `notify_email` read SMTP connection details out of that same dict:

```python
# apps/backend/src/app/workers/notification_worker.py:75-79 (before)
hostname = str(provider_config.get("smtp_host", ""))
port = int(provider_config.get("smtp_port", 587))
```

`hostname` was therefore always `""`, `aiosmtplib.send` failed, retried twice, and the alert was
logged as `notification_delivery_failed`. The **test** path meanwhile used the global `AppSettings`
SMTP config via `SmtpService`, so the operator clicked *Test*, saw success, and every real alert was
dropped. `notify_email` had no test coverage anywhere, which is why the two halves could disagree.

The fix makes one path out of the two — delivery now uses the same source the test button does,
which is also the direction INC-06 already recorded (`SECRET_KEYS["email"] = ()`, "connection
details come from the global SMTP settings"):

- `services/smtp_service.py` — new `send_alert`, the single email path for both *Test* and dispatch.
  It reuses `_connect()`, so it inherits implicit-TLS-on-465 / STARTTLS-on-587 handling and the
  vault-decrypted password rather than reimplementing them. Alerts go out as multipart
  plain + branded HTML; alert text is `html.escape`d, since titles and messages carry
  probe- and operator-authored content. `_build_message` gained an optional `plain` alternative.
  Also new: `SMTP_NOT_CONFIGURED` and `smtp_is_configured(cfg)`, shared by both callers so the
  message cannot drift apart again — them drifting apart *is* this finding.
- `workers/notification_worker.py` — `notify_email` opens its own session, reads `AppSettings`, and
  calls `send_alert` with the sink's `to`. A missing recipient and an unconfigured SMTP server each
  raise with the real cause, which `_dispatch_notification`'s retry loop turns into a
  `notification_delivery_failed` audit entry an operator can act on.
- `api/notifications.py` — `_test_email_sink` switched from `send_test_email` (which shared nothing
  with dispatch beyond the connection) to `send_alert`. Creating or patching an email sink without a
  recipient is now a 422 rather than a sink that silently drops everything routed to it.
- `pages/NotificationsPage.jsx` — the Recipient Email hint names Settings → SMTP as the source, and
  says SMTP is unconfigured when it is.

No migration and no schema change: an email sink's stored `provider_config` was already just `{to}`;
the SMTP fields it was read for were never written by anything.

### INC-03. Notification "Minimum Severity" is an exact match, not a threshold

**Resolved.** The UI labelled the route field **"Minimum Severity"** under a **"Severity Threshold"**
column, but the dispatcher compared for equality:

```python
# apps/backend/src/app/workers/notification_worker.py:255 (before)
if route.alert_severity == severity or route.alert_severity == "*":
```

A route set to `info` therefore received info alerts only — warning and critical were silently
discarded, the opposite of what the label promised and a failure in the dangerous direction. Severity
is the only routing key `NotificationRoute` has (`models.py:2276`, still no target/entity/quiet-hours
dimension), so when it filters wrongly there is nothing else to catch the alert. This mattered more
after INC-02: the email sinks that fix made functional were routed by the same broken comparison.

The fix gives the decision one owner, the way INC-06 gave sink secrets one:

- `services/notification_severity.py` — new, and the only place that decides what a threshold admits.
  `SEVERITY_LADDER` is `("info", "warning", "critical")` and position in it *is* the rank;
  `route_matches(threshold, severity)` is the whole routing predicate. Two deliberate asymmetries,
  both failing toward delivery: an alert whose severity is not on the ladder ranks as `critical` so
  it reaches every route rather than none, and a route whose stored threshold is not on the ladder
  admits everything rather than becoming a black hole. Common spellings (`warn`, `error`, `fatal`,
  `notice`, …) are folded onto the ladder on the *alert* side only — alerts arrive from any publisher
  on `alert.>`, whereas thresholds are ours and the API now rejects anything else.
- `workers/notification_worker.py` — the equality comparison is now `route_matches(...)`, and
  `process_alert` dispatches to each sink at most once per alert. That second half is not
  incidental: under exact matching at most one route per sink could match, so nothing deduplicated
  them; under a floor several can, and the operators most likely to have several are exactly the
  ones who worked around this bug. `_is_duplicate` keys on the alert (`subject:severity:title`), not
  on the sink, so it does not catch a sink selected twice — without this the fix would have turned a
  dropped-alert bug into a double-notification bug for them.
- `api/notifications.py` — `RouteCreate.alert_severity` became a `Literal` of the four values, so a
  typo is a 422 instead of a route that looks configured and delivers nothing, and the closed set
  reaches the OpenAPI schema where API clients can see it. `RouteOut` stays a bare `str`; legacy rows
  still have to serialise.
- `lib/alertSeverity.js` — new, mirroring `ROUTE_SEVERITIES`. Both surfaces that offer the field
  (`pages/NotificationsPage.jsx` and `components/settings/NotificationsManager.jsx`) read their
  options and their wording from it, so they can no longer describe the field differently: "Warning
  and above", "Critical only", "All events". The route form also carries a hint saying it is a floor.
  A stored value the API would now reject is still shown verbatim rather than hidden — an operator
  cannot fix a route whose threshold the screen refuses to name.

No migration and no schema change: every stored `alert_severity` was already one of the four values
the UI offered; only the comparison against them changed. Operators who worked around the bug by
adding one route per severity keep working — those extra routes are now redundant rather than wrong,
and the per-alert sink deduplication above keeps them from doubling every notification.

Coverage the finding blamed on nothing being tested: `tests/services/test_notification_severity.py`
pins the ladder, `tests/services/test_notification_routing.py` drives `process_alert` through it
(including the duplicate-sink case), and `tests/api/test_notification_routes_api.py` pins what the
API accepts and asserts the `Literal` and `ROUTE_SEVERITIES` still name the same four values — those
two drifting apart is this finding in miniature. `tests/services/notification_worker_harness.py` is the worker scaffolding the INC-06
dispatch tests already had, extracted so both files share it.

### INC-04. UI-created API tokens are authorized for nothing

**Resolved.** `POST /auth/api-token` never set `scopes`, and `APIToken.scopes` is
`mapped_column(JSONB, default=list)` (`models.py:2047`) — so the row stored `[]`, not `NULL`.
`_normalise_token_scopes([])` returned `()` rather than `None`, `_request_token_scopes` turned that
into `set()`, and `require_scope` took the `token_scopes is not None` branch to call
`has_scope(set(), ...)`, which is always `False` → **403 Insufficient permissions** on every
`require_scope`-guarded route: discovery, monitors, clusters, integrations, telemetry.

The fix has two halves, and the second is larger than the finding asked for:

- `core/token_scopes.py` — new, and the only place that decides what a token may be granted.
  `GRANTABLE_SCOPES` and `SCOPE_PRESETS` are served to the frontend by `GET /auth/scopes`, so the
  picker cannot offer a scope the validator rejects or the enforcement ignores. `validate_scopes`
  is the field validator on both create routes, so an unknown scope is a 422 rather than a token
  that looks configured and authorizes nothing — this finding in miniature.
- `api/auth.py` — `POST /auth/api-token` takes an optional `scopes` and falls back to
  `sorted(effective_scopes(current_user))`. A token created without an explicit choice carries its
  creator's own permissions, which is what an operator clicking *Create API token* has always meant
  by it. This is what keeps `ProfileModal.jsx`, which still sends only `label` and `expires_at`,
  from minting dead tokens.
- `core/security.py` — a stored `()` normalises to `None`, not to an empty grant. `None` means
  "unscoped: fall through to the creating user's permissions", so **every token already in the
  database starts working on upgrade** instead of having to be reissued. That widens what those
  rows can do, and deliberately: they were created as an admin's own credential and had always
  effectively been one.
- `core/rbac.py` — `require_role` now checks a scoped token against `ROLE_SCOPE_REQUIREMENT`, which
  mirrors `ROLE_DEFAULT_SCOPES` so the two cannot describe different privilege ladders. This is the
  half the finding did not ask for. It recorded that `require_role` routes "still work, because
  they resolve the creating admin and ignore token scopes" — which is a second bug wearing the
  first one's clothes. Scopes constrained the `require_scope`-guarded routers and nothing else, so
  a token minted read-only was an administrator everywhere else in the API. **A scoped token is now
  limited on role-guarded routes too.** That is a tightening: a `read:*` token that could write
  through a `require_role("editor")` route before this landed now receives 403. Session users and
  legacy unscoped tokens have `token_scopes is None`, so the branch never runs for them and their
  behaviour is unchanged.

Coverage the finding blamed on nothing exercising the UI path — every backend test built `APIToken`
rows with explicit scopes, so the one shape the UI produced was the one shape untested:
`tests/api/test_token_scopes.py` pins the create-route default and the role-gate check from both
sides, and `tests/api/test_api_tokens_admin.py` covers the administration surface (INC-14).

No migration: the `scopes` column already existed, and the `()` → `None` normalisation is what lets
existing rows work without one.

### INC-05. External-node relationship deletes are unrouted

**Resolved.** `api/external_nodes.py` defined a second `APIRouter` — `_rel_router` — carrying the
two standalone relationship deletes, and passed it to nothing. `main.py` mounted
`external_nodes.router` only, so neither path was in the route table while the module declaring them
imported cleanly. Two frontend call sites shipped against the first one:
`pages/ExternalNodesPage.jsx:331` (removing a network from an external node) and
`components/map/linkMutations.js:537` (deleting an external-node link on the map). Unlinking an
external node from a network was not possible in the product.

**Correction to the finding:** the callers got **405 Method Not Allowed**, not 404. `main.py`'s SPA
fallback `GET /{full_path:path}` matches every path but only for GET, so an unrouted `DELETE` is
answered by the method check instead of falling through to a 404. Same outcome, misleading symptom —
405 reads as "wrong verb" and sends whoever debugs it to the client.

- `api/external_nodes.py` — `_rel_router` is now `relations_router`. The rename is not cosmetic: a
  leading underscore says *module-private*, which is the wrong signal for the one router in the file
  that another module has to mount. The comment above it now states where it mounts and why it
  cannot sit under the module's own `/external-nodes/{node_id}` prefix — a link is addressed by its
  own id, not by the node it hangs off.
- `main.py` — mounted at the `/api/v1` root beside `external_nodes.router` with the same
  `require_auth` dependency. The route keeps its own `require_write_auth`, so a viewer gets 403 and
  an anonymous caller 401, matching every other write in the module.
- **`DELETE /service-external-nodes/{relation_id}` was deleted rather than mounted.** It had no
  caller, and `api/services.py:340` already exposes
  `DELETE /services/{service_id}/external-dependencies/{relation_id}`, which calls the same
  `external_nodes_service.unlink_service` and is the path `servicesApi.removeExternalDep` sends.
  Mounting it would have added a second address for one operation — the "redundant, not missing"
  class INC-19 tracks — while closing a finding about surfaces disagreeing. Its now-unreachable
  `service-external-nodes` entry in `middleware/logging_middleware.py`'s `_ENTITY_ALIASES` went with
  it; the `external-node-networks` entry beside it, written for a route that had never been live,
  starts working with this mount.

Coverage the finding blamed on nothing exercising the mounted surface — both existing frontend tests
mock `externalNodesApi` wholesale, so no test on either side had ever named the path:

- `tests/api/test_external_node_relations.py` — 204 and the row gone, 404 for an unknown relation,
  403 for a viewer, 401 unauthenticated.
- `__tests__/external-nodes-api.test.js` — pins the path `removeNetwork` sends. It and the backend
  test name each other, the two-sided pin INC-11 used.
- `tests/test_router_mounting.py` — the general guard: every `APIRouter` defined under `app.api` must
  have every route it declares present in the running app, with exemptions in `_UNMOUNTED_ROUTERS`
  that must give a reason and must still name a live router. This is the backend counterpart of
  INC-21's `nav-coverage.test.js` — a surface that exists but cannot be reached now fails a test
  instead of waiting for an audit. It was verified against the defect it exists for: with the mount
  removed it fails naming `app.api.external_nodes:relations_router` and the unrouted path.

**A second defect found while implementing this:** `security/endpoint_inventory.json` was three
routes stale. `GET /agents/server-key/pending` (INC-13), `POST /auth/api-tokens/{token_id}/rotate`
and `GET /auth/scopes` (INC-14) were all live and none was in the inventory, so
`test_full_endpoint_inventory_matches_runtime_routes` — the SEC-06 gate asserting every endpoint
declares a policy — had been failing on `dev` since those landed. `scripts/generate_endpoint_inventory.py --write`
picks up all four routes and the gate is green again. The inventory is generated rather than
hand-written, so nothing was reviewed away: all four classify as `authenticated` with role or
write-scope enforcement. **Adding a route means regenerating that file**, which is the step both
earlier findings missed.

No migration and no schema change.

## P1 — Present but non-functional, or implemented with no way to reach it

### INC-06. Notification sink secrets are stored and served in plaintext

**Resolved.** `NotificationSink.provider_config` was plain `JSONB` carrying the comment
*"(encrypted if needed) — v0.2.0"*; nothing encrypted it. `SinkOut` returned the whole dict and
`GET /notifications/sinks` requires only `require_role("viewer")`, so any viewer could read every
Slack/Discord/Teams incoming-webhook URL — each a bearer credential for posting into that channel.

The fix follows the `credential_vault.py` mechanism already used for `smtp_password_enc`:

- `services/notification_secrets.py` — new, and the only place that decides which config keys are
  secret. `encrypt_config` (write) stores `webhook_url` as `webhook_url_enc`; `decrypt_config`
  (delivery) returns plaintext; `redact_config` (read) serves a masked preview plus a
  `webhook_url_set` flag. An unknown provider type is assumed to carry a webhook URL, so a provider
  added later cannot leak by default.
- `api/notifications.py` — create/update encrypt, `SinkOut` redacts, `test_sink` decrypts. A PATCH
  carrying the mask back carries the stored ciphertext forward instead of clobbering it.
- `workers/notification_worker.py` — dispatch decrypts. It also gained `_init_vault()`, copying
  `telemetry_collector`'s pattern: `workers/main.py` never initialized the vault, so without it
  encryption would have broken delivery for *every* provider, not just email.
- `services/vault_service.py` — `rotate_vault_key` re-encrypts sink secrets and
  `_count_encrypted_secrets` counts them. Omitting this would have made the next key rotation
  silently orphan every configured webhook URL.
- `pages/NotificationsPage.jsx` — the sink form now builds `provider_config` from its declared
  fields instead of spreading the whole edit-form value bag, which had been writing the row
  envelope (`id`, a nested `provider_config`) back into the stored blob.

No migration: legacy plaintext rows are masked on read from the moment this lands, still deliver,
and are rewritten encrypted on next save.

### INC-07. Let's Encrypt certificate lifecycle is inert

`certificate_service.renew_certificate` shells out to `certbot certonly --standalone`
(`services/certificate_service.py:156-208`). Four independent reasons it cannot work in a shipped
deployment:

1. `certbot` is not installed in `Dockerfile` or `Dockerfile.mono`.
2. `--standalone` binds port 80; the container runs as non-root `breaker:1000`.
3. The ACME email is hardcoded to `admin@localhost`. `docker/.env.example:32` advertises an ACME
   email variable that no code reads.
4. On `FileNotFoundError` the function logs a warning and **returns the unchanged cert**, so
   `POST /certificates/{id}/renew` answers `200` with the old expiry. The UI shows success.

The `cert_auto_renewal` scheduled job (`main.py:1270`) therefore no-ops forever for LE certs.
Self-signed renewal works correctly.

### INC-08. Email password reset is disabled with no replacement

`POST /auth/forgot-password` and `POST /auth/reset-password` both raise `410 Gone`
(`api/auth.py:169-198`), and the UI says so in two places
(`components/auth/ForgotPasswordModal.jsx:31`, `pages/ResetPasswordPage.jsx:38`).

The supporting code is all still present and maintained: `services/password_reset_service.py`,
`services/smtp_service.py`, `services/magic_link_service.py`, `PATCH /settings/smtp`,
`POST /settings/smtp/test`, and the SMTP settings tab. The only recovery path is
*Reset With Vault Key*, which requires the operator to hold `CB_VAULT_KEY` — not a path a
non-admin user can take. Either finish the reset flow or remove the SMTP-reset scaffolding and
state the boundary in the support contract.

### INC-09. Internationalization is a shell

`i18n.js` advertises six languages (`en, es, fr, de, zh, ja`) across five namespaces, and Settings
renders a Language selector wired to `i18n.changeLanguage` (`pages/SettingsPage.jsx:611-617`).

Actual translation content per language:

| Namespace | Keys |
|---|---|
| `common.json` | 2 (`header.*` — 15 labels, `map.*` — 3 labels) |
| `settings.json` | 1 (`language`) |
| `header.json` | **0** — file is `{}` |
| `map.json` | **0** — file is `{}` |
| `hardware.json` | **0** — file is `{}` |

There are 227 distinct `t('…')` call sites in the app; only three components call `useTranslation`
at all (`MacOSDOCK.jsx`, `SettingsPage.jsx`, `OOBEWizardPage.jsx`). Everything else renders its
`defaultValue`. Note also the namespace mismatch: `header.*` and `map.*` keys live inside
`common.json`, while the `header` and `map` namespaces those components declare are empty.

Switching language changes roughly fifteen strings in the dock. `en/common.json` also still ships a
`tenants` header label for a feature removed in ADR-0003.

### INC-10. Business Intelligence has no UI

**Resolved.** `GET /intel/blast-radius/{type}/{id}`, `GET /intel/capacity-forecasts`
and `GET /intel/resource-efficiency` were implemented and backed by scheduled
jobs, with no frontend caller. Product chose to ship the screen rather than
gate the jobs off.

- `pages/IntelPage.jsx` at `/intel` — the two precomputed tables. No role gate,
  matching the router's own mount (`main.py:1927` uses `require_auth` with no
  role check).
- `components/details/BlastRadiusPanel.jsx` — mounted in `HardwareDetail`,
  `ComputeDetail`, `ServiceDetail` and `StorageDetail`, exactly `intel.py`'s
  `_VALID_TYPES`. It fetches on expand rather than on drawer mount. Zero impact
  renders as an answer, not an empty state.
- `api/intel.py` — both list responses now carry the asset's name.
  `CapacityForecastOut` joins through the existing `hardware` relationship;
  `ResourceEfficiencyOut` resolves names in one query per asset *type* present,
  never one per row, pinned by
  `test_efficiency_names_do_not_scale_queries_with_row_count`. It reuses
  `dependency_graph._MODEL_MAP` rather than keeping a second copy.
  `asset_id` is not a foreign key, so a recommendation outliving its asset yields
  a null name rather than a 500.

**One spec item delivered differently:** §8.2 called for making "the analytics
job has not run" distinguishable from "nothing to report" as a backend change.
It cannot be, without new state — the job writes rows only when it finds
something, so `max(evaluated_at)` is NULL in both cases. The empty state names
the job, its schedule, and both reasons the list can be empty.

No migration: the three tables from migration 0058 already existed.

### INC-11. Knowledge Base (OUI / hostname) has no UI and no docs

**Resolved.** `api/kb.py` implemented full CRUD plus CSV export for two
operator-editable lookup tables that feed discovery naming, with no frontend
caller, no MkDocs page, and no mention in `docs/discovery.md`. The feature was
reachable only by hand-crafting HTTP requests.

Both halves are now closed:

- `pages/KnowledgeBasePage.jsx` — admin-only, embedded as the `kb` Settings tab
  following `AdminUsersPage`'s convention, so `SettingsPage.jsx` gained one
  render line rather than a feature.
- `components/kb/kbTabs.jsx` — the two tables as declarative descriptors. The
  inline-editable set is exactly what `PUT` accepts, pinned from both sides:
  `__tests__/kb-tabs.test.js` and `tests/api/test_kb.py::
  test_update_schemas_match_frontend_editable_columns` each name the other, so
  the drift that produced INC-17 fails a test that says where to look.
  `match_type` is accepted by the API but deliberately excluded from inline
  editing — it is an enum and the inline cell editor is a bare text input.
- `components/kb/KbTable.jsx` — paging is server-driven. `EntityTable`
  paginates client-side while the KB routes cap `limit` at 500, so handing it
  one unbounded fetch would have capped the view at 500 rows while looking
  complete. A failed fetch renders an error with retry, never an empty table.
  Rows are keyed by `prefix` for OUI, since `kb_oui` has no `id` column and
  `EntityTable` hard-codes `row.id`.
- `utils/validation.js` — `normalizeMacPrefix` folds any conventional MAC
  spelling to the six bare hex characters `KbOuiCreate` requires. Without it a
  pasted `B8:27:EB` is a 422 for what an operator reasonably typed.
- `docs/knowledge-base.md`, cross-referenced from `docs/discovery.md` and added
  to the MkDocs nav.

No backend change and no migration: every route this uses already existed.

### INC-12. Audit-chain verify/repair has no UI

**Resolved.** `GET /admin/audit-log/verify-chain` and
`POST /admin/audit-log/repair-chain` were the operator tooling for the
tamper-evident hash chain and had no frontend caller.

- `components/logs/AuditChainPanel.jsx` — verifies on mount. Intact is one
  quiet line; broken is escalated, names `first_failure_id`, and states that
  repair relinks the chain but does not recover the original entries. A
  verification that could not run renders an error, never a passing state.
- Repair goes through `HighRiskConfirmDialog` (added by INC-13) with the phrase
  `REPAIR_AUDIT_CHAIN` and a ≥12-character reason. Both come from the server's
  own contract — `core/audit_chain.py:19` and `AuditChainRepairRequest`'s
  `Field(min_length=12)` — so the dialog enforces it rather than restating it.
  `api/audit.js` exports the authorization constant so the typed phrase and the
  request body read from one source.
- After a repair the panel re-verifies and refetches the log list. The repair
  entry appearing in the view is the confirmation.
- `/logs/audit` renders `LogsPage` with `auditMode`, pinning `category=audit`.
  It hides no filters: entity type, action, actor, severity, search and the
  time presets are all meaningful for audit entries.

**Two corrections found while implementing this:**

`GET /logs/audit` (`api/logs.py:237`) is **redundant, not missing** — the same
class as the `GET/PUT /hardware/{id}/ports` row already in INC-19.
`GET /logs` accepts `category` and a strict superset of its parameters. The
view uses the general route; the subset route carries a disposition comment and
is tracked for removal under INC-19.

`LogsPage` was titled **"Audit Log"** while sending no `category` parameter —
it showed every category under the audit log's name, and exported CSVs named
`circuit-breaker-audit-*.csv` containing all of them. `/logs` is now titled
"Logs" and exports `circuit-breaker-logs-*.csv`; the audit title belongs to the
view that filters for it.

No migration and no schema change.

### INC-13. Agent server-key rotation has no UI

**Resolved.** `POST /agents/server-key/rotate` and `GET /agents/server-key/status`
were implemented, along with the overlap-window columns, with no frontend
caller — a high-consequence operation with a timed window and no status display.

- `components/agents/ServerKeyRotationPanel.jsx` — admin-only, mounted on the
  Agents page, which gained an import, an `isAdmin` line and one render line and
  is otherwise untouched. Rotate is disabled during an overlap because the
  endpoint 409s then; a racing 409 refetches and shows the rotation rather than
  raising an error about it. A status read that fails renders an error state
  distinct from the idle state — "no rotation in progress" means safe, "cannot
  read status" means unknown, and the two must not look alike.
- `components/common/HighRiskConfirmDialog.jsx` — new shared type-to-confirm
  primitive, introduced here and reused by INC-12 and INC-14. Rotation confirms
  on the phrase `ROTATE`.
- `schemas/agents.py` / `api/agents.py` — `ServerKeyRotationStatus` gained a
  `fleet` adoption block computed from `server_pk_current_pinned_at` /
  `server_pk_successor_pinned_at`, the columns `models.py:432-450` added for
  exactly this and which nothing read. It is one aggregate query, pinned by
  `test_rotation_status_adoption_is_one_query_regardless_of_fleet_size`
  following `_latest_samples`' precedent. Revoked agents are excluded — they
  never handshake again and would make a finished rollout look stuck forever.
- `GET /agents/server-key/pending` — new: the agents not yet on the successor,
  by name, so an admin can chase them before the window closes. Empty rather
  than an error when no rotation is active.
- `docs/agent-key-rotation.md` — runbook, added to the MkDocs nav.

**Deviation from the design:** spec §6.3 called for a per-agent key-state column
on the fleet table. `FleetTable.jsx:18-21` documents its column list as a
contract with `FleetRow`'s hand-counted `colSpan` values
(`METRIC_COLUMN_SPAN`, `PENDING_DETAIL_SPAN`), so a *conditional* twelfth column
would have made both dynamic in the densest table in the app and reflowed the
fleet view the moment a rotation started. The same information is a drill-down
inside the panel instead.

No migration: every column this reads already existed.

### INC-14. Scoped service accounts are API-only; token admin is incomplete

**Resolved.** Four gaps left SRV-06 ("creation, least privilege, rotation, revocation, expiry")
unmet at the product surface even though most of the primitives existed: `POST /auth/service-account`
— the only way to mint a *scoped* token — had no UI; the API-token tab in `ProfileModal.jsx` sent
only `label` and `expires_at`, with no scope picker, which is what produced INC-04;
`GET /auth/api-tokens` filtered on `APIToken.created_by == current_user.id`, so one admin could
neither see nor revoke another admin's tokens; and there was no rotation endpoint at all, only
create and delete.

All four are closed, across the API and a screen:

- `api/auth.py` — `GET /auth/api-tokens` takes `scope=mine|all`, so `all` is the fleet-wide
  inventory the finding asked for, resolving each token's creator to a name in one query rather
  than one per row. `DELETE /auth/api-tokens/{id}` lets any admin revoke any token, not only their
  own. `POST /auth/api-tokens/{id}/rotate` is new: it issues a fresh secret and deletes the old row
  in one transaction, keeping the label, scopes and expiry, so rotation is not "revoke and hope you
  remember how it was configured". Every path calls `invalidate_token_cache()` — without it a
  revoked or rotated secret would keep working until the cache aged out, which is the failure mode
  a revocation feature exists to prevent.
- `GET /auth/scopes` — the catalog and presets from `core/token_scopes.py` (INC-04), so the picker
  and the validator read the same list.
- `api/tokens.js` — the frontend binding for all six routes.
- `components/settings/AccessTokensManager.jsx` — the screen. It offers the four presets by name
  rather than raw scope strings, an expiry choice, and a *Create as a service account* checkbox
  that switches the call to `POST /auth/service-account`; the inventory switches between *mine* and
  the whole install, showing each token's scopes, creator, kind, and last use. Rotate and revoke
  both go through `HighRiskConfirmDialog` (the primitive INC-13 introduced), and rotation surfaces
  the new secret once, the way creation does.
- `pages/AccessTokensPage.jsx` at `/admin/tokens`, behind `RequireAdmin` — the component landed in
  `ecc2bad5` imported by nothing, which is the state the navigation rework then found and fixed
  (INC-21). It is reachable from the Govern group in the route menu, the dock, and the command
  palette.

**One thing deliberately left as it was:** `ProfileModal.jsx` still creates tokens with a label and
an expiry and no scope choice. That is no longer a defect, because INC-04 made the create route
default to the creator's own effective scopes — the personal tab mints a personal credential, and
the administration screen is where least privilege is chosen. Giving the profile modal a second
scope picker would have made two surfaces answer the same question differently, which is the shape
of most findings in this register.

No migration and no schema change: `APIToken.scopes`, `created_by`, and `expires_at` all already
existed. Rotation reuses the existing table rather than adding a supersession column, so a rotated
token leaves no history — the audit log is where that record lives.

### INC-15. Restore is native-install-only and absent from the CLI

`cb` exposes `backup` but no `restore` (`cb:749`, usage block at `cb:715-732`), while
`deploy/scripts/restore.sh` — the only full-state restore — writes `/etc/circuitbreaker/.env` and
drives a host `psql`/`systemd` install directly. There is no restore path for the `docker` or
`compose` modes that `cb` itself supports (`cb:22-25`), and `POST /admin/db/snapshot` /
`GET /admin/db/snapshots` have no matching restore endpoint.

`docs/backup-restore.md:7` states a 4-hour RTO target. Backup is a one-command operation in every
mode; restore is a manual, mode-specific procedure in one of three.

### INC-21. `/misc` is a complete page with no way to reach it

**Resolved.** `MiscPage` renders full CRUD over `miscApi` and is routed at `/misc`, and nothing in
the product linked to it: not the route menu, not the dock, not the command palette. The only way
to open it was to type the URL.

**Why the sweep missed it.** This register's method was a route-level diff of every frontend API
call against the live FastAPI route table. `MiscPage` calls its API and the API answers, so the
diff saw a matched pair and moved on. The gap was one layer up, in the frontend's own navigation,
which that method never inspected — and no test asserted that a route was reachable, so nothing
else caught it either. The same blind spot is why the register recorded INC-14's
`AccessTokensManager` as landed while it was imported by nothing.

Closed by the navigation IA rework (`specs/2026-08-24-navigation-ia-rework-design.md`):

- `data/navigation.js` is now the single source of navigation truth — one `NAV_GROUPS` structure and
  one RBAC predicate, `canSeeNavItem`. The route menu, the dock, the dock preferences panel, and the
  command palette all derive from it instead of maintaining four separate hardcoded lists, which is
  what allowed them to disagree about what exists.
- `/misc` is listed as **Other Assets** under Inventory. `/admin/tokens` (INC-14), `/logs/audit`
  (INC-12), `/intel` (INC-10), `/agents`, `/monitors`, `/ipam` and `/privacy` gained the palette and
  preference entries they had been missing.
- `__tests__/nav-coverage.test.js` makes recurrence a test failure rather than an audit finding:
  every route in `App.jsx`'s authenticated block must appear in `NAV_GROUPS` or in `UNLISTED_ROUTES`
  with a stated reason, and every exemption must still name a live route. A parity test pins that
  the dock never offers what the menu withholds.

**A second defect found while implementing this:** the dock kept its own role filter, so a viewer
saw a **Certificates** icon the route menu hid from them. Both surfaces now share `canSeeNavItem`,
and the parity test is seeded with a viewer so the leak fails a test if reintroduced.

**Not closed, and not tracked anywhere yet:** `/privacy`, `/certificates`, and `/notifications` have
no `RequireAdmin` route guard, so their admin-only treatment in the menu is cosmetic — a
non-admin who types the URL still reaches the page. That is authorization work belonging to
`docs/1.0.0-release-readiness-audit.md`, not navigation, but nothing in either document records it
today.

No backend change and no migration.

## Suggested order of work

Thirteen of the twenty-one findings are closed: INC-01, INC-02, INC-03, INC-04, INC-05, INC-06,
INC-10, INC-11, INC-12, INC-13, INC-14, INC-17, and INC-21. **The P0 band is empty** — no surface in
the register is now both reachable and wrong.

What is left is the P1 band, in the order their answers get cheaper the earlier they are decided:

- **INC-08** (email password reset disabled with no replacement) and **INC-07** (Let's Encrypt
  lifecycle inert) are both product decisions before they are code. Each can be closed by finishing
  the feature *or* by removing the scaffolding and stating the boundary in the support contract, and
  the second is legitimate for 1.0.0. Deciding late means shipping a surface that promises something
  the build cannot do — which is what INC-07 does today, answering `200` with an unchanged expiry.
- **INC-15** (restore is native-install-only and absent from the CLI) is the one with a stated
  target it misses: `docs/backup-restore.md` claims a 4-hour RTO while restore is a manual,
  mode-specific procedure available in one of the three modes `cb` supports.
- **INC-09** (i18n is a shell) is the largest and the least urgent. The Language selector changes
  roughly fifteen strings; either wire the remaining 227 call sites or take the selector down until
  the content exists.

The P2/P3 remainder — INC-16, INC-18, INC-19, INC-20 — are cleanups that need individual
dispositions rather than a blanket rule, and none of them blocks a release.
