## P0 — Reachable and wrong

### INC-02. Email notification sink can never deliver

**Resolved.** The sink form collects only `name`, `provider_type`, `webhook_url`, `to`, `enabled`
(`apps/frontend/src/pages/NotificationsPage.jsx`), so an email sink's `provider_config` was
`{webhook_url, to}` — but `notify_email` read SMTP connection details out of that same dict:

```python
# apps/backend/src/app/workers/notification_worker.py:75-79 (before)
hostname = str(provider_config.get("smtp_host", ""))
port = int(provider_config.get("smtp_port", 587))
```

`hostname` was therefore always `""`, `aiosmtplib.send` failed, retried twice, and the alert was
logged as `notification_delivery_failed`. The **test** path meanwhile used the global `AppSettings`
SMTP config via `SmtpService`, so the operator clicked *Test*, saw success, and every real alert was
dropped. `notify_email` had no test coverage anywhere, which is why the two halves could disagree.

The fix makes one path out of the two — delivery now uses the same source the test button does,
which is also the direction INC-06 already recorded (`SECRET_KEYS["email"] = ()`, "connection
details come from the global SMTP settings"):

- `services/smtp_service.py` — new `send_alert`, the single email path for both *Test* and dispatch.
  It reuses `_connect()`, so it inherits implicit-TLS-on-465 / STARTTLS-on-587 handling and the
  vault-decrypted password rather than reimplementing them. Alerts go out as multipart
  plain + branded HTML; alert text is `html.escape`d, since titles and messages carry
  probe- and operator-authored content. `_build_message` gained an optional `plain` alternative.
  Also new: `SMTP_NOT_CONFIGURED` and `smtp_is_configured(cfg)`, shared by both callers so the
  message cannot drift apart again — them drifting apart *is* this finding.
- `workers/notification_worker.py` — `notify_email` opens its own session, reads `AppSettings`, and
  calls `send_alert` with the sink's `to`. A missing recipient and an unconfigured SMTP server each
  raise with the real cause, which `_dispatch_notification`'s retry loop turns into a
  `notification_delivery_failed` audit entry an operator can act on.
- `api/notifications.py` — `_test_email_sink` switched from `send_test_email` (which shared nothing
  with dispatch beyond the connection) to `send_alert`. Creating or patching an email sink without a
  recipient is now a 422 rather than a sink that silently drops everything routed to it.
- `pages/NotificationsPage.jsx` — the Recipient Email hint names Settings → SMTP as the source, and
  says SMTP is unconfigured when it is.

No migration and no schema change: an email sink's stored `provider_config` was already just `{to}`;
the SMTP fields it was read for were never written by anything.

### INC-03. Notification "Minimum Severity" is an exact match, not a threshold

**Resolved.** The UI labelled the route field **"Minimum Severity"** under a **"Severity Threshold"**
column, but the dispatcher compared for equality:

```python
# apps/backend/src/app/workers/notification_worker.py:255 (before)
if route.alert_severity == severity or route.alert_severity == "*":
```

A route set to `info` therefore received info alerts only — warning and critical were silently
discarded, the opposite of what the label promised and a failure in the dangerous direction. Severity
is the only routing key `NotificationRoute` has (`models.py:2276`, still no target/entity/quiet-hours
dimension), so when it filters wrongly there is nothing else to catch the alert. This mattered more
after INC-02: the email sinks that fix made functional were routed by the same broken comparison.

The fix gives the decision one owner, the way INC-06 gave sink secrets one:

- `services/notification_severity.py` — new, and the only place that decides what a threshold admits.
  `SEVERITY_LADDER` is `("info", "warning", "critical")` and position in it *is* the rank;
  `route_matches(threshold, severity)` is the whole routing predicate. Two deliberate asymmetries,
  both failing toward delivery: an alert whose severity is not on the ladder ranks as `critical` so
  it reaches every route rather than none, and a route whose stored threshold is not on the ladder
  admits everything rather than becoming a black hole. Common spellings (`warn`, `error`, `fatal`,
  `notice`, …) are folded onto the ladder on the *alert* side only — alerts arrive from any publisher
  on `alert.>`, whereas thresholds are ours and the API now rejects anything else.
- `workers/notification_worker.py` — the equality comparison is now `route_matches(...)`, and
  `process_alert` dispatches to each sink at most once per alert. That second half is not
  incidental: under exact matching at most one route per sink could match, so nothing deduplicated
  them; under a floor several can, and the operators most likely to have several are exactly the
  ones who worked around this bug. `_is_duplicate` keys on the alert (`subject:severity:title`), not
  on the sink, so it does not catch a sink selected twice — without this the fix would have turned a
  dropped-alert bug into a double-notification bug for them.
- `api/notifications.py` — `RouteCreate.alert_severity` became a `Literal` of the four values, so a
  typo is a 422 instead of a route that looks configured and delivers nothing, and the closed set
  reaches the OpenAPI schema where API clients can see it. `RouteOut` stays a bare `str`; legacy rows
  still have to serialise.
- `lib/alertSeverity.js` — new, mirroring `ROUTE_SEVERITIES`. Both surfaces that offer the field
  (`pages/NotificationsPage.jsx` and `components/settings/NotificationsManager.jsx`) read their
  options and their wording from it, so they can no longer describe the field differently: "Warning
  and above", "Critical only", "All events". The route form also carries a hint saying it is a floor.
  A stored value the API would now reject is still shown verbatim rather than hidden — an operator
  cannot fix a route whose threshold the screen refuses to name.

No migration and no schema change: every stored `alert_severity` was already one of the four values
the UI offered; only the comparison against them changed. Operators who worked around the bug by
adding one route per severity keep working — those extra routes are now redundant rather than wrong,
and the per-alert sink deduplication above keeps them from doubling every notification.

Coverage the finding blamed on nothing being tested: `tests/services/test_notification_severity.py`
pins the ladder, `tests/services/test_notification_routing.py` drives `process_alert` through it
(including the duplicate-sink case), and `tests/api/test_notification_routes_api.py` pins what the
API accepts and asserts the `Literal` and `ROUTE_SEVERITIES` still name the same four values — those
two drifting apart is this finding in miniature. `tests/services/notification_worker_harness.py` is the worker scaffolding the INC-06
dispatch tests already had, extracted so both files share it.

### INC-04. UI-created API tokens are authorized for nothing

`POST /auth/api-token` never sets `scopes` (`apps/backend/src/app/api/auth.py:497-524`), and
`APIToken.scopes` is `mapped_column(JSONB, default=list)` (`models.py:2047`) — so the row stores
`[]`, not `NULL`.

On each request:

1. `_normalise_token_scopes([])` returns `()` — an empty tuple, **not** `None`
   (`core/security.py:82-88`).
2. `_set_request_token_scopes` therefore sets `request.state.token_scopes = ()`.
3. `_request_token_scopes` returns `set()`, again not `None` (`core/rbac.py:108-112`).
4. `require_scope` takes the `token_scopes is not None` branch and calls `has_scope(set(), ...)`,
   which is always `False` → **403 Insufficient permissions** (`core/rbac.py:177-182`).

Every `require_scope`-guarded router rejects the token: discovery, monitors, clusters, integrations,
telemetry. `require_role`-guarded routes still work, because they resolve the creating admin and
ignore token scopes — so the failure is inconsistent and hard to diagnose.

Only `POST /auth/service-account` sets scopes, and it has no UI (see INC-14). Every backend test
constructs `APIToken` rows with explicit scopes
(`tests/api/test_monitor_api.py:43-50`), so the UI path is untested.

### INC-05. External-node relationship deletes are unrouted (404)

`apps/backend/src/app/api/external_nodes.py:180` defines a second router:

```python
_rel_router = APIRouter(tags=["external-nodes"])
@_rel_router.delete("/external-node-networks/{relation_id}", ...)
@_rel_router.delete("/service-external-nodes/{relation_id}", ...)
```

`_rel_router` appears nowhere else in the codebase — `main.py` mounts `external_nodes.router` only
(`main.py:1637`), and neither path is in the live route table.

Two frontend call sites hit the first one:

- `apps/frontend/src/pages/ExternalNodesPage.jsx:331` — removing a network from an external node.
- `apps/frontend/src/components/map/linkMutations.js:537` — deleting an external-node link on the map.

Both 404. Unlinking an external node from a network is not possible in the product.

## P1 — Present but non-functional, or implemented with no way to reach it

### INC-06. Notification sink secrets are stored and served in plaintext

**Resolved.** `NotificationSink.provider_config` was plain `JSONB` carrying the comment
*"(encrypted if needed) — v0.2.0"*; nothing encrypted it. `SinkOut` returned the whole dict and
`GET /notifications/sinks` requires only `require_role("viewer")`, so any viewer could read every
Slack/Discord/Teams incoming-webhook URL — each a bearer credential for posting into that channel.

The fix follows the `credential_vault.py` mechanism already used for `smtp_password_enc`:

- `services/notification_secrets.py` — new, and the only place that decides which config keys are
  secret. `encrypt_config` (write) stores `webhook_url` as `webhook_url_enc`; `decrypt_config`
  (delivery) returns plaintext; `redact_config` (read) serves a masked preview plus a
  `webhook_url_set` flag. An unknown provider type is assumed to carry a webhook URL, so a provider
  added later cannot leak by default.
- `api/notifications.py` — create/update encrypt, `SinkOut` redacts, `test_sink` decrypts. A PATCH
  carrying the mask back carries the stored ciphertext forward instead of clobbering it.
- `workers/notification_worker.py` — dispatch decrypts. It also gained `_init_vault()`, copying
  `telemetry_collector`'s pattern: `workers/main.py` never initialized the vault, so without it
  encryption would have broken delivery for *every* provider, not just email.
- `services/vault_service.py` — `rotate_vault_key` re-encrypts sink secrets and
  `_count_encrypted_secrets` counts them. Omitting this would have made the next key rotation
  silently orphan every configured webhook URL.
- `pages/NotificationsPage.jsx` — the sink form now builds `provider_config` from its declared
  fields instead of spreading the whole edit-form value bag, which had been writing the row
  envelope (`id`, a nested `provider_config`) back into the stored blob.

No migration: legacy plaintext rows are masked on read from the moment this lands, still deliver,
and are rewritten encrypted on next save.

### INC-07. Let's Encrypt certificate lifecycle is inert

`certificate_service.renew_certificate` shells out to `certbot certonly --standalone`
(`services/certificate_service.py:156-208`). Four independent reasons it cannot work in a shipped
deployment:

1. `certbot` is not installed in `Dockerfile` or `Dockerfile.mono`.
2. `--standalone` binds port 80; the container runs as non-root `breaker:1000`.
3. The ACME email is hardcoded to `admin@localhost`. `docker/.env.example:32` advertises an ACME
   email variable that no code reads.
4. On `FileNotFoundError` the function logs a warning and **returns the unchanged cert**, so
   `POST /certificates/{id}/renew` answers `200` with the old expiry. The UI shows success.

The `cert_auto_renewal` scheduled job (`main.py:1270`) therefore no-ops forever for LE certs.
Self-signed renewal works correctly.

### INC-08. Email password reset is disabled with no replacement

`POST /auth/forgot-password` and `POST /auth/reset-password` both raise `410 Gone`
(`api/auth.py:169-198`), and the UI says so in two places
(`components/auth/ForgotPasswordModal.jsx:31`, `pages/ResetPasswordPage.jsx:38`).

The supporting code is all still present and maintained: `services/password_reset_service.py`,
`services/smtp_service.py`, `services/magic_link_service.py`, `PATCH /settings/smtp`,
`POST /settings/smtp/test`, and the SMTP settings tab. The only recovery path is
*Reset With Vault Key*, which requires the operator to hold `CB_VAULT_KEY` — not a path a
non-admin user can take. Either finish the reset flow or remove the SMTP-reset scaffolding and
state the boundary in the support contract.

### INC-09. Internationalization is a shell

`i18n.js` advertises six languages (`en, es, fr, de, zh, ja`) across five namespaces, and Settings
renders a Language selector wired to `i18n.changeLanguage` (`pages/SettingsPage.jsx:611-617`).

Actual translation content per language:

| Namespace | Keys |
|---|---|
| `common.json` | 2 (`header.*` — 15 labels, `map.*` — 3 labels) |
| `settings.json` | 1 (`language`) |
| `header.json` | **0** — file is `{}` |
| `map.json` | **0** — file is `{}` |
| `hardware.json` | **0** — file is `{}` |

There are 227 distinct `t('…')` call sites in the app; only three components call `useTranslation`
at all (`MacOSDOCK.jsx`, `SettingsPage.jsx`, `OOBEWizardPage.jsx`). Everything else renders its
`defaultValue`. Note also the namespace mismatch: `header.*` and `map.*` keys live inside
`common.json`, while the `header` and `map` namespaces those components declare are empty.

Switching language changes roughly fifteen strings in the dock. `en/common.json` also still ships a
`tenants` header label for a feature removed in ADR-0003.

### INC-10. Business Intelligence has no UI

`GET /intel/blast-radius/{type}/{id}`, `GET /intel/capacity-forecasts`, and
`GET /intel/resource-efficiency` are implemented and backed by scheduled `analytics_job` and
`retention_job` (`main.py:1321,1327`) plus three tables from migration 0058. No frontend code calls
any of them.

`docs/business_intelligence.md:5-6` is honest about it — *"In 1.0 these are API-only capabilities …
no screen in the app calls them"* — so this is a known deferral rather than a surprise. It is
listed here because a whole computed subsystem with a scheduler cost and no user surface is a 1.0
scope decision: ship a screen, or gate the jobs off by default.

### INC-11. Knowledge Base (OUI / hostname) has no UI and no docs

**Resolved.** `api/kb.py` implemented full CRUD plus CSV export for two
operator-editable lookup tables that feed discovery naming, with no frontend
caller, no MkDocs page, and no mention in `docs/discovery.md`. The feature was
reachable only by hand-crafting HTTP requests.

Both halves are now closed:

- `pages/KnowledgeBasePage.jsx` — admin-only, embedded as the `kb` Settings tab
  following `AdminUsersPage`'s convention, so `SettingsPage.jsx` gained one
  render line rather than a feature.
- `components/kb/kbTabs.jsx` — the two tables as declarative descriptors. The
  inline-editable set is exactly what `PUT` accepts, pinned from both sides:
  `__tests__/kb-tabs.test.js` and `tests/api/test_kb.py::
  test_update_schemas_match_frontend_editable_columns` each name the other, so
  the drift that produced INC-17 fails a test that says where to look.
  `match_type` is accepted by the API but deliberately excluded from inline
  editing — it is an enum and the inline cell editor is a bare text input.
- `components/kb/KbTable.jsx` — paging is server-driven. `EntityTable`
  paginates client-side while the KB routes cap `limit` at 500, so handing it
  one unbounded fetch would have capped the view at 500 rows while looking
  complete. A failed fetch renders an error with retry, never an empty table.
  Rows are keyed by `prefix` for OUI, since `kb_oui` has no `id` column and
  `EntityTable` hard-codes `row.id`.
- `utils/validation.js` — `normalizeMacPrefix` folds any conventional MAC
  spelling to the six bare hex characters `KbOuiCreate` requires. Without it a
  pasted `B8:27:EB` is a 422 for what an operator reasonably typed.
- `docs/knowledge-base.md`, cross-referenced from `docs/discovery.md` and added
  to the MkDocs nav.

No backend change and no migration: every route this uses already existed.

### INC-12. Audit-chain verify/repair has no UI

`GET /admin/audit-log/verify-chain` and `POST /admin/audit-log/repair-chain`
(`api/admin_audit.py:22,35`) are the operator tooling for the tamper-evident audit hash chain.
Neither is called from the frontend.

`GET /logs/audit` (`api/logs.py:237`) is likewise never called — `LogsPage` uses `GET /logs` only
(`api/client.jsx:409`). `docs/audit-log.md:48` describes *"filters at the top of the page"* for a
dedicated audit view that does not exist as a distinct surface.

### INC-13. Agent server-key rotation has no UI

`POST /agents/server-key/rotate` and `GET /agents/server-key/status` are implemented, along with the
overlap-window columns `agent_server_key_pending_private_key`,
`agent_server_key_rotation_started_at`, and `agent_server_key_rotation_overlap_expires_at`
(`models.py:1489-1493`). Neither endpoint has a frontend caller.

Rotating the key that authenticates the entire agent fleet is a high-consequence operation with a
timed overlap window and no status display. It needs a screen, or an explicit `cb` subcommand plus
a runbook.

### INC-14. Scoped service accounts are API-only; token admin is incomplete

- `POST /auth/service-account` — the only way to mint a *scoped* token — has no UI.
- The API-token tab in `ProfileModal.jsx` sends only `label` and `expires_at`; there is no scope
  picker, which is what produces INC-04.
- `GET /auth/api-tokens` filters on `APIToken.created_by == current_user.id`
  (`api/auth.py:545-551`), so one admin cannot see or revoke another admin's tokens. There is no
  fleet-wide token inventory.
- There is no rotation endpoint — only create and delete.

Together these leave SRV-06 ("creation, least privilege, rotation, revocation, expiry") unmet at the
product surface even though most of the primitives exist.

### INC-15. Restore is native-install-only and absent from the CLI

`cb` exposes `backup` but no `restore` (`cb:749`, usage block at `cb:715-732`), while
`deploy/scripts/restore.sh` — the only full-state restore — writes `/etc/circuitbreaker/.env` and
drives a host `psql`/`systemd` install directly. There is no restore path for the `docker` or
`compose` modes that `cb` itself supports (`cb:22-25`), and `POST /admin/db/snapshot` /
`GET /admin/db/snapshots` have no matching restore endpoint.

`docs/backup-restore.md:7` states a 4-hour RTO target. Backup is a one-command operation in every
mode; restore is a manual, mode-specific procedure in one of three.

## P2 — Narrower gaps

### INC-01. Racks removed from the backend, residual references in the backend

**Resolved.** Product chose to complete the removal rather than reinstate racks; the frontend and
the backend have both been brought in line.

Migration `f61dd2dc9ade_remove_deprecated_features` (2026-07-14) dropped the `racks` table and the
`hardware.rack_id / u_height / rack_unit / mounting_orientation / side_rail` columns. The backend
kept nothing: there is no `Rack` model, no `api/racks.py`, and no `/racks` route in the live route
table. The frontend has now been brought in line — `racksApi`, `useRacksData.js`, the entire
orphaned `components/racks/` tree, the `u_height` / `rack_unit` hardware form fields, the
`grid_rack` map layout (with a fallback for operators whose stored `graph_default_layout` still
names it), the "By Rack" grouping, the discovery bulk "Rack Placement" section, and the `rack` audit
entity filter are all gone. `docs/hardware.md` and `docs/topology-map.md` no longer describe them.

The backend remainder has now been cleared as well:

- `apps/backend/src/app/schemas/rack.py` — deleted; `RackCreate/RackUpdate/RackOut` were orphaned.
- `apps/backend/src/app/services/bulk_suggest.py` — the hard-`[]` `rack_suggestions` key is gone
  from both return paths and from the docstring.
- `apps/backend/src/app/services/graph_layout.py` — the `grid_rack` / "Rack Grid" catalog entry is
  gone. `useMapLayout.js` keeps `grid_rack` in `RETIRED_LAYOUT_ENGINES` so an operator whose stored
  `graph_default_layout` still names it falls back cleanly.
- `apps/backend/src/app/schemas/hardware.py` — `mounting_orientation` / `side_rail` removed
  (INC-17), along with the stale `# v0.1.2: rack positioning` / `# v0.1.4-cortex: rack assignment`
  comments left above the removed fields.
- Residual prose references in `api/graph.py`, `api/ws_topology.py`, `core/subjects.py`,
  `schemas/discovery.py`, and `services/discovery_merge.py` docstrings/comments.

What remains is history only: the `f61dd2dc9ade` and `0060_hardware_mounting_fields` migrations
(both required for upgrade paths), the guarded `ix_hw_rack_id` entry in `0035_performance_indexes_v2`
(skipped when the column is absent), and `db_rewrite_proposal/models.py`, which is a design
artifact rather than live code.

### INC-16. Integration connection test covers only two providers

`integration_provider_service.test_config` dispatches to `_test_proxmox` and `_test_docker` and
returns `{"status": "error", "message": "Test not implemented for provider '<provider>'"}` for
anything else (`services/integration_provider_service.py:158-166`). The surrounding
`/integrations/{provider}/config` CRUD is generic over provider, so the UI can create a config it
cannot validate. Either constrain the provider set to what `test_config` supports, or return a
distinguishable "test unsupported" state the UI renders as such rather than as a failure.

### INC-17. `mounting_orientation` / `side_rail` are accepted and discarded

**Resolved.** Both fields survived in `HardwareBase` and `HardwareUpdate` but their columns were
dropped by `f61dd2dc9ade`: `create_hardware` enumerates its columns explicitly and never passed
them, and `update_hardware` `setattr`d them onto a non-mapped attribute that was discarded at
commit — the API accepted the values, returned 200, and stored nothing. Both fields are now removed
from the schemas, so the API no longer advertises or accepts them. Same root cause as INC-01, fixed
with it.

### INC-18. `show_experimental_features` is exposed but never read

Present on `AppSettings` (`models.py:1299`) and in `schemas/settings.py:98`, with a dedicated
migration (`0011_pg_show_experimental_boolean`). No backend or frontend code reads it. Either wire
it to a real gate or drop it from the settings schema.

Each is either a screen that was never built or a route that should be deleted. They need
individual dispositions, not a blanket rule.

### INC-20. Residual dead code and tenant remnants

- `apps/frontend/src/api/discovery.js:34` — `getResult` calls `GET /discovery/results/{id}`, which

## Already tracked elsewhere
