# Circuit Breaker 1.0.0 Release-Readiness Audit

**Audit date:** 2026-08-10  
**Audited revision:** `49c5b775` (`dev`)  
**Current canonical version:** `0.3.5` in `VERSION`  
**Scope:** Read-only, whole-repository review of product behavior, cb-agent, architecture, security,
reliability, end-to-end quality, operations, packaging, documentation, media, and repository hygiene.
The only repository change made by this audit is this document.

## Executive decision

**Current recommendation: NO-GO for 1.0.0.**

The project has a substantial feature set and an unusually strong automated baseline for a beta:
2,166 backend tests, 385 frontend tests, race-tested Go agent packages, native and container release
paths, security workflows, backup/restore tooling, and a composed cb-agent release-gate test. It is
closer to a serious server product than the version number suggests.

It is not ready for the stability and trust implied by 1.0.0 because several release-blocking
conditions remain:

1. **Tenant isolation is non-functional.** PostgreSQL RLS is explicitly disabled for the application
   role, the tenant session variable is set at the wrong lifecycle boundary, and most service queries
   are not tenant-scoped. This creates cross-tenant read/write risk.
2. **Authenticated data can be read without an auth dependency.** The monitor list, detail, history,
   events, probe-run, overview, summary, and uptime routes have no read authorization dependency.
3. **cb-agent has not completed its real-world acceptance bar.** The long composed Docker journey is
   manual-only, forced rollback and malformed/oversized wire frames are delegated to other tests, and
   the core remote-site claim has not been exercised across real NAT/firewall/latency conditions.
4. **The release has no single reproducible acceptance matrix.** CI covers fast suites and builds,
   but not the 30–40 minute agent journey, fresh-install/upgrade/restore matrices across supported
   platforms, browser E2E, or packaged-artifact acceptance.
5. **The server-product contract is not yet explicit.** Circuit Breaker already runs as a server,
   but headless operation, API stability, lifecycle semantics, worker topology, resource limits,
   remote administration, compatibility, and support boundaries are not defined as a versioned
   product surface.
6. **Release housekeeping is visibly incomplete.** Some version sources disagree,
   contributor/security contact text contains placeholders, generated/user artifacts are tracked,
   and the root `npm test` intentionally fails. Historical README/gallery screenshots were restored
   during follow-up work but still require a 1.0 freshness and anonymization review.

Security and data-integrity blockers should be fixed before feature expansion. The cb-agent polish
and server-application track can then become the two headline 1.0 workstreams.

## Release-blocking findings

### P0 — Security and trust

#### R1. Repair and prove tenant isolation

Current evidence:

- Migration `0040_rls_policies.py` executes `ALTER ROLE breaker SET row_security = off`.
- `db/session.py` calls `set_config(..., true)` during connection checkout, outside the correct
  request transaction boundary, and uses an empty string for no tenant.
- Only a small subset of application queries include `tenant_id` predicates.
- Core resources use primary-key lookup or unscoped selects.

Required outcome:

- Decide whether 1.0 is genuinely multi-tenant. If yes, make tenant context mandatory after login,
  repair RLS transaction semantics, remove the application-role bypass, and add application-layer
  tenant predicates as defense in depth.
- If multi-tenancy is not a supported 1.0 feature, remove or hard-disable the misleading tenant UI,
  routes, middleware, and claims instead of shipping a non-functional boundary.
- Add a cross-tenant matrix covering every tenant-owned entity and nested route for read, create,
  update, delete, search, export, WebSocket/SSE, background jobs, and ID enumeration.
- Test both database policy enforcement and API enforcement. Include missing/invalid tenant context,
  pooled-connection reuse, concurrent tenants, worker jobs, and administrative override behavior.

**Gate:** no cross-tenant access in automated adversarial tests; RLS is verified using the actual
production application role.

#### R2. Apply authentication and authorization uniformly

Current monitor GET routes lack read dependencies. Conduct an automated route inventory rather than
fixing only this router: classify every HTTP, WebSocket, SSE, metrics, health, bootstrap, public,
download, upload, and agent endpoint as public-by-design or protected, with an explicit dependency.

Required outcome:

- Add read scope/tenant checks to monitor routes and verify nested monitor data cannot cross tenants.
- Maintain a checked-in public-route allowlist and fail CI when a new route has no declared policy.
- Reassess the pre-OOBE admin-equivalent window; require a one-time setup token or bind bootstrap to
  localhost/private setup context.
- Re-verify MFA + forced password change, lockout ordering, session revocation, OAuth callback code
  handling, public-status information disclosure, and proxy-aware rate-limit identity.

**Gate:** authorization matrix tests for anonymous, viewer, demo, editor, admin, masqueraded admin,
expired/revoked session, wrong tenant, and agent identity.

**Progress — 2026-08-24 (partial).** The reachability-and-authorization batch
(`specs/2026-08-24-reachability-authorization-design.md`) closed the route-guard half of this
finding and corrected the API gates behind it. R2 stays open: the full matrix across demo,
masqueraded admin, expired/revoked session, and agent identity is not yet written.

What changed, and what an operator will notice:

- **Editors can no longer manage notification sinks or routes.** All nine routes on that surface
  now require admin. Sink `provider_config` carries webhook URLs, which are bearer credentials for
  posting into a channel. This is a deliberate tightening: an editor who administers sinks today
  loses that access and must be made an admin or have the work reassigned.
- **Viewers can no longer list certificates.** `GET /certificates` was ungated while the menu hid
  it, so the inventory — issuer, subject, and expiry for every TLS surface — was readable by any
  authenticated caller.
- **Viewers can no longer suppress privacy findings.** `POST` and `DELETE
  /privacy-findings/ignore` now require admin. Suppressions a viewer created before this remain in
  place; only new ones are refused.
- **Viewers can now see the Privacy page in navigation.** Its reads were always open to every
  authenticated user; the menu was hiding a page the API served. Nothing was loosened — the page's
  writes are the ones just gated.
- **Route authorization has one owner.** `apps/frontend/src/data/routeGuards.js` declares the role
  for every route; `App.jsx` enforces it through a single `Guarded` component and
  `data/navigation.js` derives each menu item's gate from it. A menu entry can no longer be more
  permissive than the route it points at, and adding a page forces an authorization decision
  rather than defaulting to open.
- **New build gate:** `test_no_write_route_is_merely_authenticated` fails the build when a mutating
  route sits at authenticated-session with no role. It is the structural companion to SEC-06's
  generated inventory, which cannot see the difference because it is generated from the same code.
  On its first run it caught `POST/PUT/DELETE /topologies` and `PUT /topologies/{id}/nodes`, which
  let any viewer create, rename, delete, or re-lay-out a saved topology; they now take
  `require_write_auth`. Twenty-two exemptions remain, each with a stated reason, and a stale
  exemption fails its own test.

#### R3. Close current and systemic security debt

Required before release:

- Upgrade or otherwise resolve `click 8.3.1` / `PYSEC-2026-2132` and rerun the Python audit.
- Resolve DNS-rebinding SSRF for outbound webhooks by pinning the validated address or enforcing an
  egress allowlist/proxy. Repeat the review for every outbound integration.
- Move rate limiting to shared Redis storage and derive client identity only from trusted-proxy data.
- Fail closed if Redis/NATS/vault secret material is missing or empty.
- Sanitize or disallow uploaded SVG active content.
- Verify audit-chain serialization under concurrent writes; a hash chain that can fork under load is
  tamper-evident only in the single-writer case.
- Add SAST/dependency suppressions with owner, reason, expiry, and compensating control. Do not let
  historical reports serve as the current source of truth.

**Gate:** current CodeQL, Semgrep, Bandit, Trivy, Checkov, Gitleaks, npm audit, pip-audit, Go
vulnerability scan, container scan, and secret scan are green or have reviewed, expiring exceptions.

#### R4. Prove backup, restore, migration, and upgrade safety

For a server application, lossless recovery is a core feature, not operational documentation.

Required matrix:

- Fresh install on every supported distribution/architecture and both documented container modes.
- Upgrade from each promised supported prior version to the 1.0 release candidate.
- Failed migration rollback/recovery; interrupted package install; interrupted database migration.
- Backup while the system is active; restore to a clean host; restore after version upgrade; restore
  with agents, encrypted integration secrets, uploads, audit data, telemetry, and tenant data.
- Disk-full, permission, corrupt archive, checksum mismatch, missing vault key, incompatible schema,
  and partial snapshot cases.
- Automated restore verification that compares row counts, key entities, secrets usability, agent
  reconnection, and audit-chain validity—not merely process health.

**Gate:** documented recovery point objective (RPO), recovery time objective (RTO), tested retention,

## Server-application direction

Circuit Breaker is already deployed as a server process, but its product experience is still
primarily “a web UI that happens to have a backend.” The recommended evolution is **not** a second
parallel product. Make the existing backend a clearly defined, headless-capable control-plane server,
with the web UI as its first client and `cb` as its administrative client.

### Recommended 1.0 architecture contract

```text
Web UI / cb CLI / documented API clients
                 |
        versioned control-plane API
                 |
   API process + dedicated worker services
                 |
 PostgreSQL | Redis | NATS | object/file storage
                 |
     outbound-connected cb-agent fleet
```

The mono image can remain the easiest single-node appliance. The production server mode should use
separate supervised services and make the following explicit:

- **Control plane:** authenticated, tenant-aware, versioned REST/WebSocket/SSE API.
- **Workers:** discovery, notifications, telemetry ingest, integrations, monitor scheduler/poller,
  cleanup/rollups, and agent dispatch, each with ownership and idempotency rules.
- **State:** PostgreSQL as source of truth; Redis/NATS as disposable coordination layers unless a
  feature explicitly promises durable delivery; uploads/object storage covered by backup policy.
- **Clients:** web UI served separately or disabled; `cb` supports health, config validation,
  migrations, backup/restore, users/tokens, agent status, and diagnostics without browser access.
- **Compatibility:** API version policy, database migration policy, agent/server compatibility
  window, deprecation process, and upgrade order.

### Server-mode work required

1. **Headless mode.** Start API/workers without bundled frontend, weather/geocoding calls, or UI-only
   assumptions. Publish OpenAPI and stable machine-readable error contracts.
2. **Service topology.** Remove ambiguity between in-process workers and dedicated workers. Prevent
   duplicate scheduling/ingest when both modes are accidentally enabled. Expose per-worker readiness,
   lag, last success, queue depth, and graceful-drain state.
3. **Lifecycle.** Separate liveness, readiness, startup, and dependency health. Readiness must fail
   when the instance cannot safely serve writes, not merely when the process answers HTTP.
4. **Graceful operation.** Prove SIGTERM draining, job lease handoff, reconnect storms, rolling
   restart, migration coordination, and no duplicate notifications/monitor executions.
5. **Configuration.** One documented precedence order for config file, environment, database
   settings, and CLI flags. Add `cb config validate` and redact secrets in diagnostics.
6. **Administration.** Add scoped API tokens/service accounts, rotation, audit, and documented CLI
   workflows. Avoid requiring browser sessions for routine server operations.
7. **Resource profiles.** Publish minimum/recommended CPU, RAM, disk, and database sizing for small,
   medium, and agent-fleet installations. Bound queues, retention, uploads, logs, and agent spools.
8. **Deployment choice.** Clearly label mono container as single-node appliance and split services as
   production/scalable mode. State whether HA is unsupported in 1.0 or prove it.
9. **Observability.** Stable Prometheus metrics, structured logs, correlation/request/job IDs,
   redaction tests, dashboards, alert examples, and support-bundle generation.
10. **Remote access.** Document secure reverse proxy, trusted proxies, TLS ownership, firewall ports,
    agent outbound endpoints, certificate renewal, air-gap limitations, and threat model.

### Explicit non-goals to decide before 1.0

Record these in an architecture decision record (ADR):

- Single-node only versus supported high availability.
- Linux-only server and Linux-only agent versus broader OS promises.
- PostgreSQL versions and Timescale requirements.
- IPv6 support level.
- Internet-exposed operation versus trusted-LAN/VPN-only support.
- Multi-tenancy as a supported security boundary.
- Offline/air-gapped updates and agent enrollment.
- Public API/SDK stability versus internal API only.

## Reliability and implementation gaps

### Data and concurrency

- Define transaction boundaries and idempotency keys for every background job and agent dispatch.
- Prove PostgreSQL advisory-lock behavior under multiple API/worker processes.
- Test duplicate, reordered, delayed, and replayed NATS/agent frames.
- Make Redis/NATS outage behavior explicit: reject, queue, degrade, or retry; never silently drop.
- Bound telemetry, audit, events, scans, uploads, logs, and spool growth. Verify retention jobs.
- Load-test migration 0100+ indexes and the 216-migration upgrade chain at realistic fleet size.
- Add audit-chain concurrency tests and a supported chain-repair/verification procedure.

### Process and network reliability

- Replace broad exception swallowing in listeners/streams with classified, rate-limited logging and
  metrics; silent failure is especially risky in WebSocket/SSE and discovery code.
- Treat un-awaited coroutine warnings in discovery tests as defects. They can hide tests that do not
  execute the intended asynchronous path.
- Remove deprecation warnings before their upstream removal becomes an emergency upgrade blocker.
- Verify proxy headers, client IP, HTTPS detection, secure cookies, WebSocket URL construction, and
  rate limits in every documented deployment topology.
- Add long-duration soak tests for API, workers, agent reconnect, telemetry, monitors, and retention.

### Product behavior that needs a 1.0 decision

- Monitoring maintenance windows are described as future work; decide whether 1.0 alerts without
  maintenance windows are acceptable and document the limitation prominently.
- Decide which discovery mechanisms are stable versus beta, and label them consistently in UI/docs.
- IPv6 is not comprehensively supported by network ACL/discovery logic; either implement it or state
  IPv4-only support.
- Define destructive-action safeguards for clear-lab, restore-with-wipe, tenant deletion, agent
  revoke/uninstall, and bulk discovery imports.
- Add export/import interoperability and a documented data-ownership escape hatch for users.
- Provide a privacy model for discovered device data, uploaded images, credentials, telemetry, and
  external threat/weather/geocoding calls.

  backup/restore, agent protocol/update, audit, secrets, and destructive admin actions; establish a
  repo-wide ratchet above the present 55% after measuring exclusions.

- Add mutation testing selectively to auth/tenant/protocol validators and property/fuzz tests to
  parsers, CIDRs, URLs, frame codecs, imports, and backup manifests.
- Add Playwright browser E2E. Component tests do not prove routing, real API cookies/CSRF, WebSockets,
  responsive layout, focus behavior, or absence of console/runtime errors.
- Add visual regression for topology, discovery, agents, monitors, settings, auth/OOBE, empty/error
  states, and desktop/mobile viewports.
- Track skips and xfails with issue, owner, reason, and expiry. Fail on unexpected new warnings.
- Add test sharding and deterministic seed/reporting; retain JUnit, coverage, logs, traces, screenshots,
  and container diagnostics.
- Test the artifacts users install, not only source trees and locally built services.

- frontend `package.json`: `0.3.5`

Make `VERSION` the only hand-edited value and add a CI check that all generated/runtime displays,
artifact names, agent manifests, Docker labels, release tags, and documentation agree. Avoid build
scripts that modify tracked manifests as a side effect.

### npmjs packaging and distribution

Add npmjs as a supported 1.0 distribution channel only after defining exactly what the package is.
The current root package is an application-repository manifest: it is marked `private`, has no
executable entry point, and depends on repository-local backend, frontend, Go, database, and service
assets. Publishing it as-is would create a package that installs successfully but cannot operate as
Circuit Breaker.

Recommended package model:

- Publish a dedicated package such as `@blkleg/circuitbreaker` or `@blkleg/cb-cli`, rather than
  turning the repository root into the registry artifact.
- Prefer a small, cross-platform **administration/installer CLI** that can validate prerequisites,
  download the correct signed release artifact, verify its checksum/signature/provenance, install or
  update it, and invoke documented server-management commands.
- Do not embed the full frontend `node_modules`, Python environment, PostgreSQL, Redis, NATS, or Go
  agent inside a generic npm tarball. The native packages and container image should remain the
  authoritative server payloads.
- If the intended npm package is instead an API client/SDK, give it a separate package name,
  TypeScript declarations, supported API-version range, generated contract tests, and independent
  semantic-versioning policy.

Required package contents and metadata:

- A dedicated package directory with `name`, canonical version, description, keywords, MIT license,
  repository, homepage, bugs, funding/support links, `engines`, `os`, `cpu`, `bin`, `files`, exports,
  and package-manager compatibility documented accurately.
- A minimal allowlisted tarball produced with the `files` field and `.npmignore` defense in depth.
  It must exclude `.env` files, credentials, uploads, test fixtures containing secrets, build caches,
  internal reports, source maps unless intentional, and unrelated monorepo content.
- `npm pack --dry-run` and unpacked-tarball inspection in CI, with package size and file-count limits.
- Install and command-smoke tests from the packed `.tgz` in clean Linux, macOS, and Windows runners
  for every platform the CLI claims to support.
- Tests for offline/error behavior, unsupported OS/architecture, proxy configuration, interrupted
  download, checksum/signature mismatch, insufficient permissions, upgrade, rollback, and uninstall.
- No install-time download or privileged mutation in `preinstall`/`postinstall`. Downloads and system
  changes should occur only after an explicit user command with clear confirmation and audit output.
- Exact version parity among npm package, `VERSION`, Git tag, GitHub Release, downloaded artifacts,
  container labels, and CLI-reported version.

Registry ownership and supply-chain requirements:

- Reserve and verify the chosen npm organization/package name; require organization MFA and at least
  two maintainers with recovery ownership documented.
- Publish from GitHub Actions using npm trusted publishing/OIDC and provenance instead of a long-lived
  automation token wherever supported.
- Use protected npm environments and require the complete release/security gate for the exact commit
  before publish. A Git tag alone must not authorize publication.
- Publish release candidates under `next` (for example `1.0.0-rc.1`) and move `latest` only after the
  installed tarball passes acceptance. Never overwrite or unpublish a released stable version as a
  normal rollback mechanism; deprecate it and publish a corrected patch.
- Generate an npm-compatible SBOM or include the package in the release SBOM, retain provenance, and
  scan both the packed tarball and its installed dependency tree.
- Enable registry access controls, provenance display, package integrity monitoring, and an emergency
  compromise/revocation procedure. Document who can publish and how access is reviewed.

Documentation required:

- Add an npm installation page that explains whether npm installs the server CLI, installer, or SDK;
  prerequisites; supported Node versions/platforms; required privileges; proxy/offline behavior;
  update/uninstall commands; telemetry/network behavior; and how signature verification works.
- Keep the native package/container installation methods prominent. Do not imply that
  `npm install -g` alone runs the complete server if it only installs a management CLI.
- Publish copy-paste examples for `npm`, `npx`, and the chosen package manager only when each path has
  an automated acceptance test.

**npmjs release gate:** a clean runner installs the exact packed tarball, verifies provenance and the
downloaded server artifact, performs a smoke install/status/update/uninstall journey, and confirms
that the npm registry version, Git tag, application version, checksums, and SBOM all match.

## Performance and capacity gates

Create reproducible datasets and publish results for at least:

- 1k, 10k, and target-maximum inventory entities/edges.
- 10, 100, and target-maximum connected agents.
- Concurrent telemetry, discovery, monitoring, notification, and integration activity.
- API p50/p95/p99 latency, WebSocket fan-out, queue lag, DB connections/locks, CPU/RAM, and disk growth.
- Frontend startup/bundle size, large-table behavior, topology render/interaction frame rate, and
  reconnect behavior.
- 24-hour and 7-day soak runs with retention and backup jobs enabled.

Set supported limits from evidence. Fail gracefully before limits rather than allowing unbounded
queues, scans, graph rendering, or disk consumption.

## Prioritized delivery plan

## 1.0.0 release gate checklist

Do not tag 1.0.0 until every mandatory item is evidenced:

- [ ] Tenant boundary is either fully enforced and adversarially tested or explicitly removed.
- [ ] Every route/stream has an explicit public/auth/RBAC/tenant policy; monitor reads are protected.
- [ ] Current dependency, SAST, secret, IaC, container, and supply-chain gates are green.
- [ ] cb-agent composed E2E is stable, automated for release, and real remote-site UAT is signed off.
- [ ] Fresh install succeeds from published artifacts on every supported OS/architecture.
- [ ] GitHub issues #66–#101 have installed-artifact evidence; #101's ARM64 AVIF crash, `_MEI`
  accumulation, and string `environment_id` defects are fixed and regression-tested.
- [ ] Supported-version upgrade matrix passes; failed-upgrade recovery is proven.
- [ ] Backup/restore drill meets documented RPO/RTO and restores encrypted/agent/upload data.
- [ ] Browser E2E, accessibility, responsive, and console-health gates pass.
- [ ] Failure-injection and graceful-shutdown/restart gates pass for DB, Redis, NATS, workers, and WAN.
- [ ] Performance, retention, queue, and disk limits are measured and documented.
- [ ] API/agent/database compatibility and deprecation policies are published.
- [ ] Version sources and release artifacts agree exactly.
- [ ] README/docs have no broken links or missing media; support/security contacts are real.
- [ ] License and contributor documents are correct; repository generated/user artifacts are cleaned.
- [ ] Signed artifacts, checksums, SBOMs, provenance, and verification instructions are published.
- [ ] The dedicated npm package has an explicit purpose, minimal allowlisted contents, accurate
  metadata, secured ownership, trusted publishing, provenance, and no privileged install scripts.
- [ ] The exact npm `.tgz` passes clean-runner install/status/update/uninstall tests and matches the
  Git tag, application version, downloaded artifact checksums, and SBOM.
- [ ] No unexplained skips, xfails, async warnings, lint warnings, or release exceptions remain.
- [ ] Release notes include known limitations, migration steps, rollback, and security posture.
- [ ] A release owner signs the final acceptance matrix and rollback plan.

## Bottom line

Circuit Breaker should treat 1.0 as the point where it becomes a dependable **server control plane
with a web client and remote agents**, not merely the point where the visible feature list feels
large enough. The fastest credible route is:

1. close the security boundaries;
2. finish and field-test cb-agent;
3. formalize the server/headless/worker contract;
4. prove install, upgrade, restore, browser, and failure behavior from release artifacts; and
5. clean the public repository and documentation so they accurately describe the product users get.

Until those gates are met, continue beta/RC versioning and avoid implying internet-safe, multi-tenant,
or long-term compatibility guarantees that the current evidence does not support.
