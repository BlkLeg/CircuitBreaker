## Product behavior

Ship `@blkleg/circuitbreaker` as a dedicated, small npm package. Keep both existing
manifests private. Linux only; claim CPU/distro combinations only after packed-package
smoke tests against the release support matrix. Node's minimum supported version is
an implementation decision to validate in CI before publishing.

The CLI handles everyday management and explicit install, update, downgrade,
rollback, and uninstall. Reuse the shell installer, install identity, diagnostics,
backup/restore code, and native command implementation. JavaScript coordinates
selection, verification, planning and presentation; shell owns privileged execution.
Installing/updating the npm package itself never changes the server or runs an
installer. No lifecycle hook downloads, privilege elevation or service restart.

The package version stays in lockstep with its release. The installed server can be
older: `version` reports CLI version, server version, artifact digest, install mode,
and compatibility separately. A compatibility table gates management of older
servers; never infer compatibility solely from semver or matching version strings.

## Entrypoint and command contract

Use `circuitbreaker` as the npm binary. Preserve `/usr/local/bin/cb` as the existing
native binary: avoid two installations competing for the same executable name.
Both expose the same management behavior; long-form npm lifecycle commands provide
the new orchestration. Add native `cb` lifecycle forwarding to the verified npm
launcher when present, using an absolute recorded path and a recursion guard, so
existing operators can also use `cb install`, `cb update`, `cb downgrade`, and
`cb rollback`. Direct shell installation remains available without Node; if the
launcher is absent, native commands retain their supported behavior and print the
applicable shell recovery path. npm's bin target launches directly, with argument arrays and
inherited signals; never compose a shell command from user arguments.

| Proposed command | Behavior |
| --- | --- |
| `circuitbreaker` / `help` | Concise grouped help; identity and recovery hints when relevant. |
| `install [--version VERSION] [--channel stable\|candidate]` | Fresh install. Defaults to this CLI's exact release, unless explicitly selecting a channel. Existing install produces a plan and directs to update. |
| `update [--version VERSION] [--channel stable\|candidate]` | Explicit check for an eligible newer release, plan, backup, apply, health check. Stable by default. |
| `update --check` | Read-only release/compatibility check. No privileged changes. |
| `downgrade --version VERSION` | Older target only; explicit compatibility check and data-impact plan. |
| `rollback [--operation ID]` | Restore last committed recovery point or the selected retained operation, including matching data if required. |
| `history [--json]` | Show lifecycle operations and available recovery points, without secrets. |
| `recover --operation ID` | Inspect interrupted operation, reconcile actual state, propose safe resume or rollback. |
| `cli update [--version VERSION]` | Update the npm tool only through its recorded npm install context; otherwise print the exact applicable npm command. Never update the server implicitly. |
| `uninstall` | Reuse native removal and data-retention prompts; npm tool remains installed. |

Carry over `info`, `status`, `resources`, `doctor`, `diag bundle`, `setup`,
`setup-token`, `logs`, `restart`, `backup`, `restore`, `migrate`, `token`, `user`,
`agent`, `config validate`, `vault-recover`, and `version`, preserving arguments,
streaming and existing command exit codes. Forward to a validated absolute native
CLI path from trusted identity/mode metadata, not to a `cb` discovered arbitrarily
on PATH. Missing identity means diagnosis, never guessed container names or ports.

Lifecycle flags: `--plan`, `--yes`, `--json`, `--verbose`, `--no-color`,
`--local-bundle PATH`, `--airgap`. `--plan` makes no system changes but may fetch
metadata unless air-gapped. `--json` emits one final structured result; phase events
are available separately through `--events=jsonl`. Native JSON schemas remain
unchanged. Noninteractive mutation requires `--yes`; data restore additionally
requires an explicit `--restore-data` acknowledgment. `--yes` cannot waive
compatibility, verification, backup or privilege failures. Help/version/status
never perform automatic update checks. No prompt-based full-screen chat interface. Preserve installer options for port,
FQDN, certificate type, email, data directory, TLS and Docker mode; validate and
forward these explicitly. Supplying both `--version` and `--channel` is an error.
An older target supplied to `update` redirects to an explicit downgrade plan, never
performs an implicit downgrade; the current target is a successful no-op.

## Install and update transaction

1. Discover platform, identity, current version/schema and installation ownership.
   Acquire a host operation lock; reject overlapping npm or shell lifecycle runs.
2. Resolve the target once to an immutable release/tag, exact asset, checksum,
   signature and provenance. Check source/target compatibility before proceeding.
3. Stage in a private directory, using bounded downloads, proxy support, timeout,
   capped retries, disk-space checks and atomic finalization. Resume only when
   immutable identity matches; reverify the complete result. No mutable `latest`
   lookup after planning, including the installer executable.
4. Verify the release's signature, provenance and digest against pinned trust and
   expected repository/workflow/tag/platform. Archive traversal and symlink checks
   precede extraction. Air-gap mode requires the full offline verification set
   and performs zero outbound requests. No npm `--skip-checksum` escape hatch.
5. Display current → target version, mode, downtime expectation, migration/data
   impact, backup/recovery path, and verified release identity; obtain confirmation.
6. Elevate only the native mutation helper. Revalidate staged content and identity
   under privilege; reject changed plans. Do not run npm or the entire Node frontend
   under sudo. Backend backup and mutation occur under the same exclusive lock.
7. Create a verified recovery point: old release, units/configuration, install
   identity, database snapshot and application-managed persistent assets. Keep
   secrets in protected recovery storage, outside logs and the journal. Verify
   actual database connectivity; a stopped PgBouncer is never grounds to skip backup.
8. Invoke the verified, target-bound installer with the verified local bundle.
   Preserve existing dependency/bootstrap/install logic while preventing independent
   downloads, repeated prompts and competing progress renderers.
9. Start the service, wait for bounded readiness, compare reported version/schema
   and identity to the plan, then atomically commit operation history. Success means
   the expected version is healthy, not merely that the process exited zero.

Existing package-owned installations stay with their package manager. Docker mode
uses exact image digests and recorded Compose/container settings, with its own
volume recovery point. Proxmox mutation runs inside the identified CT; installing
npm on its host does not silently select a guest. Every native management command
carries over, while lifecycle mutations refuse modes without tested adapters.

## Downgrade and rollback

These are different operations. Downgrade selects an older release; rollback restores
a known recovery point for a particular operation. Never run an older application
against an unvalidated newer database or assume Alembic migrations are reversible.

- Compatible schema: retain current data, stage older signed release, snapshot current
  state, activate and verify. Show that data is retained in the plan.
- Incompatible schema with a matching recovery point: offer that point explicitly.
  Show backup timestamp and the fact that newer writes will be lost if restored.
  Require `--restore-data` as well as normal confirmation for unattended operation.
- Incompatible schema without a matching recovery point: refuse before service stop.
  Explain the missing prerequisite and offer history/backup inspection. No `--force`.
- Legacy release with missing trust/compatibility metadata: unsupported downgrade,
  with a clear reason. 0.4.7 does not automatically certify every previous release.
- Post-1.0 policy currently rejects downgrades. That policy remains in force for those
  targets until deliberately amended; 0.4.7 compatibility must be explicit.

After activation failure, automatic recovery is allowed only to a verified,
preauthorized point and only when no unaccounted writes can be lost. Gate external
writes through the health/commit boundary. If data may have changed, require an
explicit restore decision. Report both attempted target and resulting running
version. A recovered failure still exits nonzero; failed recovery retains artifacts
and prints a precise recovery command. Never label manual intervention as success.

Journal operation ID, old/target identities and digests, adapter, backup references,
phase transitions and verification outcomes. Use root-owned, atomic records and
restricted permissions. On restart inspect real files, units and schema before
resuming; interrupted database migration is not blindly retried. Ctrl-C before
mutation cleans transient staging; after mutation it requests a safe checkpoint
and preserves recovery metadata. A killed process remains discoverable in history.
Retain the last successful recovery point by default; never prune the sole point
needed by an unfinished operation. Shared lock/state belongs to the install, not
an individual user's npm cache.

## Terminal design and motion

Keep `cb_logo` byte-identical. Its orange (ANSI 209), purple (141), violet (99) and
charcoal (238) are the terminal identity. Improve spacing, hierarchy and lifecycle
copy around it; no raster artwork, replacement mascot, or animated ASCII figure.
Display the full existing art once for interactive install at ≥66 columns when
height permits. Routine commands use a compact title. Narrow terminals get a text
heading rather than wrapped artwork. Repeated headers never clear scrollback.

Use one renderer for npm and direct shell entrypoints. The native helper emits
versioned events on a dedicated descriptor; raw output remains in the redacted log.
Standalone shell execution continues using its own renderer. Native passthrough
commands keep their existing output, including resource watch and log streaming.

Completed phases become permanent check-mark rows with durations. One small live
region contains the active phase, measurable progress, elapsed time, and detail.
Download progress uses bytes/total bytes; known substeps use completed/total.
Unknown work gets a spinner and elapsed time, not a fabricated percentage. Show
phase ordinal, rather than pretending weighted installer progress measures time.
At most 8 redraws/second; a subtle orange activity marker supplies motion while
purple marks the active phase. Show a slow-work message based on observed timing;
ETA appears only with defensible measurements. Never reach 100% before health passes.

Example active update (illustrative timing):

```text
Circuit Breaker   UPDATE   native / linux-amd64
0.4.6 → 0.4.7   Signed release verified

✓ Preflight and compatibility                       0.8s
✓ Download and verify                   84 / 84 MiB  7.2s
✓ Recovery point saved                              4.1s
◌ Apply release                            4 / 6    12.3s
  Preparing database migrations · services paused

Recovery: op-20260930-001
Log: /var/log/circuitbreaker/install.log
```

Failure freezes the final active row and shows cause, resulting system state,
backup/operation ID, log path and one actionable command. Success shows verified
running version, health, URL from install identity, duration and rollback reference.
Never print setup tokens in routine success output; keep `setup-token` explicit.

TTY without color still gets readable symbols/labels. `TERM=dumb`, redirected
output and CI use append-only plain lines with no cursor control or art. Unicode
fallback uses `[ok]`, `[running]`, `[failed]`. Provide `--no-animation` for static
phase transitions; respect reduced-motion settings when available. Resize safely,
restore cursor on exit, and bound output to terminal width. No mouse-only controls.

## Architecture and current gaps

Proposed package: `packages/cli/`, with bin launcher, command parser, identity reader,
release resolver/verifier, lifecycle planner, native bridge and terminal renderer.
Bundle only allowlisted CLI files and pinned trust material; no server/frontend
payload or repo-wide dependencies. Record compatibility metadata in release assets.

Current code supplies a useful base: `install.sh` has staged downloads, SHA256
verification, seven-phase UI and offline inputs; `deploy/setup.sh` has backup and
upgrade; `cb` has mode-aware management and Docker recovery guidance. It does not
already supply the whole contract above. In particular, checksum verification is
not signature/provenance verification; the upgrade backup can be skipped when
PgBouncer is inactive; current snapshots are not automatically complete version
recovery points. `.prev` files and old containers alone cannot reverse data changes.

The command previews also require native full-state backup routing: the current
`cmd_backup` dispatch has Docker/Compose and package/binary branches, while install
identity maps native installations to `native`. Wire that mode to the shared
snapshot builder before shipping the proposed native `cb backup` flow. Its
post-build verification checks archive structure and the database checksum; a
restore rehearsal is a separate operation, not implied by a verified archive.
Interactive log formatting must preserve source order, multiline messages and
unstructured fallback lines; redirected output keeps its streaming contract.

Implement the native lifecycle/event/recovery contract first, then npm orchestration.
Avoid shipping a wrapper that looks polished but cannot prove the recovery path.

## Delivery sequence and release acceptance

1. Command/identity parity, compatibility manifest and bin coexistence.
2. Signed immutable staging and privilege boundary; native phase event contract.
3. Verified backup, exclusive lock, operation journal, update and readiness commit.
4. Tested downgrade/rollback/recover, including interrupted migrations and writes.
5. Shared terminal rendering, packed-package journeys, npm release channel wiring.

Gate 0.4.7 on packed `.tgz` smoke tests for every claimed host, full command parity,
no npm-hook mutation, invalid signature/provenance/checksum rejection before mutation,
air-gap zero-network behavior, proxy/offline/interruption failure paths, missing
privileges, concurrent operations, backup failure with database down, health failure
and automatic recovery, compatible downgrade, incompatible downgrade refusal,
explicit data restore, legacy missing metadata, JSON/exit contracts, terminal resize,
plain output, cursor restoration, and unchanged banner. Use isolated signed fixtures
and disposable hosts; never test lifecycle operations against a developer's install.

Proposed lifecycle exit codes: 0 success/no change; 2 invalid usage; 3 unsupported
platform/mode/compatibility; 4 network; 5 trust verification; 6 permission;
7 backup/preflight; 8 activation failed but recovered; 9 recovery/manual intervention;
10 operation lock busy; 130 interruption. Native forwarded commands retain their
existing codes. Results include schema version, operation ID, outcome, current and
target versions, recovery availability and redacted error details.

Publish with protected release approval, packed-tarball allowlist/size checks,
version parity, SBOM, trusted publishing/provenance and governed `next`/`latest`
promotion per ADR 0006. Do not add npm instructions to installation docs before the
package is actually published and passes its gates. This design changes no running
service, release version, public install instructions or npm publishing state.
