corrections below are binding on this plan; where the route text and this section disagree,

**C3. Three of the four "nav-critical" endpoints cannot become `def`.** Route slice 2.5 says

`db: Session = Depends(get_db)`. Twenty-four more use `db: Annotated[Session, Depends(get_db)]`

**C5. H5 and H6 are both real but weaker than the route states.**
- *H5*: `useMapRealTimeUpdates.js` already has per-node backoff (`BASE_DELAY` 30s,
  exponential to `MAX_DELAY` 300s, pause after `PAUSE_AFTER_ERRORS = 3`). It is **not** a
  guaranteed 429 storm. What is real: 8 nodes × 2 polls/min = 16 req/min against a

- *H6*: `useServerLifecycle.js:62-83` has zero consecutive-failure tolerance — one aborted

  `MAX_OFFLINE_BEFORE_NOTIFY_MS = 10_000` (`lib/constants.js:32`,
  `ServerLifecycleBanner.jsx:43-50`), so it takes ~5 consecutive failed polls to unmount, not
  one. The zero-tolerance state flip is still the defect to fix; the "one slow poll unmounts
  the app" framing is not accurate and must not appear in a commit message or test name.

**H7 is confirmed exactly as the route states** — `useMapTabs.js:12-35` has no `.catch`, no
`error` state, and `setLoading(false)` only on the two success branches.

## Global Constraints

These bind every task. A reviewer checks each one.

1. **`make lint` and `make verify` must pass** before any task is reported DONE. `make verify`
   is the pre-push gate (~3m20s). Never lower the coverage ratchet
   (`apps/frontend/vitest.config.ts`: statements 38 / branches 31 / functions 30 / lines 40)
   to make a build green.
2. **Python**: snake_case, full type annotations — mypy runs with `disallow_untyped_defs`.
   Docstrings on classes and public functions. Services hold logic; routes stay thin.
   Sessions via `Depends(get_db)`.
3. **Frontend**: `.jsx` for components (PascalCase), `.js` for hooks (`useCamelCase`) and API
   modules. **All HTTP goes through the axios client in `src/api/client.jsx` — no inline
   `fetch`.** Always render loading and error states.
4. **API**: snake_case JSON, errors as `{"detail": "..."}`, correct HTTP codes.
5. **Backward compatible.** Self-hosters upgrade on their own schedule and a half-updated
   deployment must still work. Migrations use `ADD COLUMN IF NOT EXISTS`; add fields alongside
   old ones rather than renaming or dropping. No endpoint may change its existing response
   shape — add fields, never remove or rename.
6. **Air-gap is first-class.** `CB_AIRGAP=true` must block outbound calls. All server-side
   outbound HTTP is constructed in `app.core.egress` and a T0 AST ratchet
   (`tests/build/test_phase1_policy_ratchets.py`) enforces it. No new task may import `httpx`
   or `requests` outside that helper.
7. **No placeholders.** No `TODO`, bare `pass`, or `NotImplementedError` left behind.
8. **Instrumentation must be production-safe and on by default only where it is free.**
   Anything with measurable cost is env-gated and off by default. No instrumentation may
   log or buffer credentials, tokens, or PII — the existing redaction filters
   (`core/log_redaction.py`) apply to any new log record.
9. **Commits**: `feat:` / `fix:` / `chore:` / `docs:`. One logical change per commit.
10. **Tests are required.** Backend: `apps/backend/tests/` (unit, no DB) or `tests/integration/`
    (needs Postgres, run via `make test-backend`). Frontend: `apps/frontend/src/__tests__/*.test.jsx`
    (vitest + testing-library). Repo-policy/static gates: `tests/build/`. A test that asserts
    nothing is a defect.
11. **Do not modify** `apps/frontend/e2e/navigation.spec.ts` or
    `apps/frontend/e2e/agent-monitor-vantage.spec.ts`. They are the wedge instrument (route §4).

## Task 1 — Backend correlation and loop instrumentation

**Route slice:** 2.1 (server half). **Depends on:** nothing.

### Why

Route §7 DoD requires "Instrumentation from Phase 2.1 shipped (request IDs, loop-lag, nav ring
buffer) — production-safe mode only." Nothing correlates a browser navigation to the server
work it caused, and there is no way to see whether the event loop is blocked. Both are
prerequisites for Tasks 5, 6 and 8.

### Ground truth (verified 2026-08-31)

- **No request-ID concept exists anywhere in the backend.** `grep -rE 'request[-_]?id|correlation'`
  over `apps/backend/src/app/` returns zero matches.
- **Middleware registration order** is in `apps/backend/src/app/main.py:1683-1705`. Starlette
  wraps in reverse, so the *last* `add_middleware` call is outermost. Current order of calls:
  `CORSMiddleware` (1683), `CSRFMiddleware` (1690), `LegacyTokenMiddleware` (1691),
  `LoggingMiddleware` (1692), `WriteAdmissionMiddleware` (1697), `SecurityHeadersMiddleware`
  (1698), `TenantRateLimitMiddleware` (1699), `TenantMiddleware` (1700), `HttpMetricsMiddleware`
  (1705). The comment at 1701-1704 states `HttpMetricsMiddleware` is added last **on purpose**
  so it is outermost and measures everything including other middleware.
- **`HttpMetricsMiddleware`** lives at `apps/backend/src/app/core/slo_metrics.py:167-202`. The
  process-lifetime registry is `REGISTRY` at `slo_metrics.py:43`.
- **`circuitbreaker_http_request_duration_seconds`** already exists — a Histogram with labels
  `[method, route]` and buckets `(0.005,0.01,0.025,0.05,0.1,0.25,0.5,1.0,2.5,5.0,10.0)` at
  `slo_metrics.py:63-69`. Route labels are templated by `_route_label` (`slo_metrics.py:137-164`)
  to bound cardinality. **Do not add a second duration histogram.**
- **No event-loop-lag metric exists.** Confirmed by grep for `event.?loop.?lag|loop_lag`.
- **Logging is plain stdlib**, no structlog, no JSON formatter, no `dictConfig`. Two
  `logging.Filter` subclasses are installed globally for **redaction**:
  `_OAuthScrubFilter` (`main.py:123-132`, attached at `main.py:135`) and `LogRedactionFilter`
  (`core/log_redaction.py:40-60`, installed by `install_global_log_redaction()` at
  `log_redaction.py:72-94`, called from `main.py:136` onto the root logger plus `uvicorn`,
  `uvicorn.error`, `uvicorn.access`, `app`).
- **`LoggingMiddleware`** (`apps/backend/src/app/middleware/logging_middleware.py:268-411`) is
  the **audit-log writer**, not a request tracer. It only fires for `POST/PATCH/PUT/DELETE`
  (line 279-280) and skips `_SKIP_PATHS` (lines 21-24). Do not extend it.
- **`core/otel.py`** gates entirely on `CB_OTEL_ENDPOINT` (`otel.py:12`); `init_otel(app)` is a
  no-op when unset and is called from `main.py:1676`.
- **Sync engine** is `apps/backend/src/app/db/session.py:37`, `pool_timeout=5` at line 43.

### What to build

**1a. Request-ID middleware.** New module `apps/backend/src/app/middleware/request_id.py`.

- A `contextvars.ContextVar[str | None]` named `request_id_var`, default `None`, exported so
  loggers and DB listeners can read it without threading it through call signatures.
- An ASGI middleware class `RequestIdMiddleware` that, per request: reads the inbound
  `X-Request-ID` header if present **and syntactically valid**, otherwise mints
  `uuid.uuid4()`. Validity rule: at most 64 characters, and only `[A-Za-z0-9_.-]`. An inbound
  value failing that is discarded and replaced with a minted one — never echoed. This stops a
  client injecting newlines or control characters into log lines.
- Sets the contextvar, and sets `X-Request-ID` on the outgoing response headers.
- Resets the contextvar in a `finally` so nothing leaks between requests.
- Register it in `main.py` **as the new outermost middleware** — that is, as the *last*
  `add_middleware` call, after `HttpMetricsMiddleware` at line 1705. Update the explanatory
  comment at 1701-1704 so it names the new outermost layer and says why the request ID must be
  established before metrics: a request ID minted inside the metrics layer cannot appear in
  the metrics layer's own log lines.

**1b. Request ID in log records.** Add a `logging.Filter` (in the same module) that sets
`record.request_id` from the contextvar, using the literal `"-"` when there is none, so format
strings never raise. Install it alongside the existing redaction filters — extend
`install_global_log_redaction()` in `core/log_redaction.py` **or** add a parallel installer
called from the same place in `main.py` (line 136). Whichever you choose, the request-ID
filter must be attached to the same logger set the redaction filter uses, and **redaction must
still run** — do not replace a filter, add one.

**1c. Event-loop lag gauge.** In `core/slo_metrics.py`, on the existing `REGISTRY`:

- `circuitbreaker_event_loop_lag_seconds` — **Gauge**, no labels, the most recent observed lag.
- `circuitbreaker_event_loop_lag_seconds_hist` — **Histogram**, no labels, buckets
  `(0.001, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0)`.

Sampler: an `asyncio` task that loops `await asyncio.sleep(0.1)` and records
`max(0.0, actual_elapsed - 0.1)` using `time.perf_counter()`. Start it in the FastAPI lifespan
in `main.py` (the lifespan starts at line 549 and yields at line 1558 — start the sampler on
the startup side, and cancel-and-await it on the shutdown side). It must:
- be cancellable, and swallow `asyncio.CancelledError` cleanly on shutdown;
- never raise into the lifespan;
- be skipped entirely when `CB_LOOP_LAG_SAMPLER=false` (default: enabled — a 100 ms sleep loop
  is free, and Global Constraint 8's gate is for things with measurable cost).

**1d. Slow-query logging.** A SQLAlchemy `before_cursor_execute` / `after_cursor_execute`
listener pair on the sync engine that logs any statement exceeding a threshold at WARNING,
including the current request ID from the contextvar. Threshold from `CB_SLOW_QUERY_MS`,
default `100`. Set `CB_SLOW_QUERY_MS=0` to disable. Log the statement **without** parameter
values — parameters carry user data and the redaction filter is a regex net, not a guarantee.
`scripts/bench-topology.py` already demonstrates the `before_cursor_execute` listener pattern
against this engine; follow it.

### Tests

Add `apps/backend/tests/core/test_request_id.py` and `apps/backend/tests/core/test_loop_lag.py`
(unit, no DB — match the existing convention in `apps/backend/tests/core/`).

Assert at minimum:
- a request with no `X-Request-ID` gets one in the response, and it is a valid UUID4;
- a request with a valid inbound `X-Request-ID` gets **that same value** echoed back;
- an inbound value containing a newline, a control character, or more than 64 characters is
  **replaced**, and the response header contains neither the injected content nor a newline;
- the contextvar is `None` after a request completes (no leak between requests);
- a log record emitted during a request carries that request's `request_id`; one emitted
  outside carries `"-"`;
- the redaction filter still redacts after the request-ID filter is installed — assert a
  bearer token in a log message is still masked;
- the loop-lag sampler records a sample and, after a deliberate synchronous block (e.g.
  `time.sleep(0.3)` inside a coroutine), the gauge reflects a lag materially above zero;
- the sampler stops cleanly on cancellation and does not raise.

### Acceptance

`make verify` green. `curl -i` on any endpoint shows an `X-Request-ID` response header.
`GET /api/v1/metrics` exposes `circuitbreaker_event_loop_lag_seconds`. No new duration
histogram was added. No `httpx`/`requests` import outside `core/egress.py`.

## Task 2 — Frontend request-ID propagation and navigation ring buffer

**Route slice:** 2.1 (browser half). **Depends on:** Task 1 (the server must echo the header).

### Why

Route §4.2 defines the correlation path: browser nav-ID → request-IDs issued during that
navigation → server logs → DB slow queries. Task 1 built the server half. This is the browser
half, and it is what Task 8's wedge spec reads to decide *which* hypothesis a captured wedge
supports.

### Ground truth (verified 2026-08-31)

- **`apps/frontend/src/api/client.jsx`** (610 lines) is the single axios instance:
  `baseURL: '/api/v1'`, `timeout: 20000`, `withCredentials: true` (lines 52-57).
  - **Request interceptor** (lines 75-95): strips `password` when `password_hash` is present;
    deletes `Content-Type` for `FormData`; injects `X-CSRF-Token` from the `cb_csrf` cookie on
    mutating methods (`CSRF_METHODS = ['post','put','patch','delete']`, line 71).
  - **Response interceptor** (lines 97-183): calls `recordServerDate(response.headers)` on
    success (98-108) and on failure (114); retries safe methods (`get/head/options`) up to 2
    times on network errors or 5xx-except-503 with backoff `500 * 2^(n-1)` capped at 4000 ms
    (lines 120-128, via `config._retryCount`); a single 429 retry that sleeps `retry-after`
    seconds, default 5 (lines 131-136, guarded by `config._retried429`); session-expiry
    detection dispatching `cb:session-expired` (lines 151-158); synthetic
    `isNetworkError` for responseless failures (139-144).
  - There is **no ring buffer and no request-ID injection** in this file today.
- **No diagnostics surface exists.** The only candidate host is the admin-only
  `SettingSection title="Host Diagnostics"` panel at
  `apps/frontend/src/pages/SettingsPage.jsx:1773`, which currently wraps `<HostStatsPanel />`.
- **Test infra**: vitest 4 + `@testing-library/react` 16, jsdom, setup file
  `apps/frontend/src/__tests__/setup.js`, `testTimeout: 15_000`. All tests live flat in
  `apps/frontend/src/__tests__/*.test.jsx`. Commands: `npm test` → `vitest run --passWithNoTests`;
  `npm run test:coverage` is what the ratchet gate uses.
- **Routing**: 25 routes, all `React.lazy` behind **one shared `Suspense`**
  (`apps/frontend/src/App.jsx:44-70,137-154`). react-router v7 wraps navigations in
  `React.startTransition` by default.

### What to build

**2a. Ring buffer module.** New `apps/frontend/src/lib/diagnosticsBuffer.js`.

- A fixed-capacity circular buffer holding the **last 200** entries. Two record kinds,
  distinguished by a `kind` field: `'request'` and `'nav'`.
- API: `recordRequest(entry)`, `recordNav(entry)`, `getEntries()` (newest last),
  `clearEntries()`, `exportJson()` returning a JSON string.
- **It must never throw into a caller.** Every public function wraps its body so that a
  failure inside diagnostics can never break a page render or an HTTP call. This is
  instrumentation; it is not allowed to be the thing that breaks.
- Memory-bounded by construction — a fixed-size array with a write index, not an array that
  grows and is sliced.
- Records **no request or response bodies**, no headers other than the request ID, and no
  query string. URL is recorded as the **path only** (strip `?` and everything after) —
  query strings carry tokens and search terms. This is Global Constraint 8.

**2b. Request-ID injection and timing.** In `client.jsx`:

- In the existing request interceptor, generate a UUID (use `crypto.randomUUID()` with a
  `Math.random`-based fallback for jsdom/older browsers) and set it as the `X-Request-ID`
  header. Stash it and a `performance.now()` start stamp on the config object, following the
  established `config._retryCount` / `config._retried429` convention (`_requestId`, `_startedAt`).
- In **both** branches of the response interceptor, call `recordRequest` with:
  `{kind:'request', requestId, method, path, status, durationMs, retryCount, wasRateLimited}`.
  `status` is `0` for a responseless network error.
- **Preserve every existing behavior**: the retry loop must reuse the *same* request ID across
  retries of one logical request (so a wedge trace shows one ID with `retryCount: 2`, not three
  unrelated IDs), CSRF injection is unchanged, `recordServerDate` still runs on both paths, and
  the 429 sleep is unchanged. Task 4 changes the 429 behavior for background polls — not this task.

**2c. Navigation marks.** New `apps/frontend/src/hooks/useNavigationTiming.js`.

- On a route change, `performance.mark('nav:start:<path>')` and record a `'nav'` entry opened.
- On the newly-rendered route's mount effect, `performance.mark('nav:end:<path>')`, close the
  entry with `durationMs`, and record it.
- A `PerformanceObserver` for `longtask` entries; attribute any long task landing between a
  nav's start and end to that nav as `longTasks: [{startTime, duration}]` and
  `longTaskTotalMs`. **`PerformanceObserver` and the `longtask` entry type are not supported
  in every browser or in jsdom** — feature-detect and degrade to an empty list rather than
  throwing.
- A nav that never closes is the wedge signal. Give the open entry a `pending: true` field
  cleared on close, so Task 8 can count `pending` entries without inferring from timestamps.
- Mount the hook once, in `App.jsx`, inside the router context but **above** the route tree so
  it observes every navigation. Do not put it in `AppInner` beside `useDiscoveryStream()` if
  that would widen what re-renders — route §4 H3 already suspects that component of a
  re-render storm, and this task must not make it worse.

**2c-bis. Expose the buffer to automation.** Task 8's Playwright spec reads the buffer via
`page.evaluate`, so it must be reachable from the page. Attach a **read-only accessor** to
`window` — `window.__cbDiagnostics = { getEntries, exportJson }` — and nothing else. Do not
expose `recordRequest`/`recordNav`/`clearEntries` on `window`; automation reads, it does not
write. Guard the assignment so it is a no-op where `window` is undefined.

**2d. Export surface.** Extend the admin-only "Host Diagnostics" `SettingSection` at
`SettingsPage.jsx:1773` with a control that downloads `exportJson()` as a file
(`circuitbreaker-diagnostics-<ISO timestamp>.json`) and a control that clears the buffer.
Render loading and error states per Global Constraint 3. Keep it admin-gated exactly as the
surrounding section already is.

### Tests

Add `apps/frontend/src/__tests__/diagnostics-buffer.test.jsx` and
`apps/frontend/src/__tests__/api-client-request-id.test.jsx`.

Assert at minimum:
- the buffer holds exactly 200 entries under 500 writes, and the retained entries are the
  **newest** 200 in order;
- a throwing argument (a value that fails `JSON.stringify`, e.g. a circular object) does not
  propagate out of `recordRequest`;
- query strings are stripped — record a URL with `?token=secret` and assert the stored path
  contains neither `?` nor `secret`;
- the axios request interceptor sets an `X-Request-ID` header, and a successful response
  records one entry carrying that same ID;
- a failed request records an entry with the right status, and a network error records
  `status: 0`;
- **a retried request records one entry with `retryCount` incremented, not three entries**;
- CSRF header injection still happens on a POST after the change (regression guard on the
  existing interceptor).

### Acceptance

`make verify` green, coverage ratchet not lowered. A manual navigation produces a `nav` entry
whose `requestId` values match `X-Request-ID` headers visible in the network panel.

## Task 4 — Batch telemetry endpoint (H5)

### Why

### What to build

**8a. A new opt-in spec** `apps/frontend/e2e/nav-wedge.spec.ts`, plus a dedicated Playwright
project for it in `playwright.config.ts` following the `visual-*` precedent
(`testMatch: /nav-wedge\.spec\.ts/`, and `testIgnore` it from the four default projects so it
never runs in the normal shards).

The spec:
- Runs the route §4.3 journey — `/map` (wait for canvas) → `/monitors` → `/map` → `/agents` →
  `/settings` → `/map` — repeated to a configurable count, default enough to be meaningful
  (the known_bugs sample was ~180 navigations) and overridable by env var so CI can run a
  short pass and a human can run a long one.
- Applies **CPU throttling** via CDP (`Emulation.setCPUThrottlingRate`, 6× per §4.3). CDP is
  **Chromium-only** — the spec must state that plainly and skip with a clear message on other
  engines rather than silently passing. The historical repro was Firefox under host
  contention; note in a comment that this spec's throttle is a different pressure source and
  is not a claim of equivalence.
- Counts a **wedge** as: URL changed to the target route, and the target route's content is
  still not rendered after a generous timeout (>5 s per §4.4). Assert on the rendered DOM, not
  only the URL — that distinction is the whole point of the bug.
- On each wedge, dumps the Task 2 ring buffer (via `page.evaluate`) alongside Playwright's
  trace, video and screenshot, into the run's artifact directory. This is what makes §4.4's
  decision tree walkable: chunk pending at wedge time → H1; chunk resolved with a long task →
  H4; all requests slow → server side.
- Reports the **wedge rate** (wedges / navigations) as a machine-readable artifact, not only
  as console output.

**8b. Do not touch the existing instrument.** Global Constraint 11 and route §4:
`navigation.spec.ts` and `agent-monitor-vantage.spec.ts` are not to be modified, quieted,
retried harder, or made less strict. If they fail while you work, that is a finding to report
in the task report — **not** something to fix by editing them.

**8c. Wire it in as opt-in.** Add a `workflow_dispatch`-able path to run it (a make target, or
a job gated behind dispatch/label — pick one and justify it in the task report). It must
**not** join the default `browser-e2e` shards: at ~1-in-60 it would add a flaky failure to
every PR, which is precisely why `known_bugs` says the suite does not assert on it.

- the two protected specs are unmodified — assert their content hash or their presence

- `nav-wedge.spec.ts` is excluded from the default projects — a contract test that reads
